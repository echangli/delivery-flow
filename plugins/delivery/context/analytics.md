# Аналитика ⟪ADAPT: ваша платформа аналитики⟫ — как устроена в коде + seed событий

> 🔧 **ADAPT — это болванка-шаблон.** Здесь живут **факты кода** вашей аналитики и **рецепт проверки**, что
> событие ушло. Грузи **по требованию** (шаг 2.4 Трека A, правка трекинга в B/C) — не в каждой сессии.
> Общий обзор продукта — `context/platform.md`.

> **Правила разметки (нейминг, каталог свойств, категории, reuse-first, депрекейт) — зона аналитика**, живут
> в скилле **`event_tagging`** (`${CLAUDE_PLUGIN_ROOT}/skills/event_tagging/reference/`:
> `naming-conventions.md`, `property-catalog.md`, `taxonomy-snapshot.md`, `example-specs/`). Здесь их
> **нет** — только факты кода и рецепт проверки. Спека событий для фичи — через скилл (`track-a.md`
> шаг 2.4), не «на глаз».
>
> MCP платформы аналитики нужен только для спеки/проверки событий (`delivery_setup §2.6в`). Проект
> аналитики: ⟪ADAPT: имя/URL вашего проекта аналитики, prod `appId`⟫; отдельный тестовый проект под
> dev/стейдж — см. §1.

## 1. Как шлётся аналитика (код)

⟪ADAPT: как в коде логируется событие — какая функция/пакет, сигнатура вызова (имя события + свойства),
список трекеров-получателей, опции вроде «дождаться идентификации пользователя». Отметь правило «не терять
вызовы логирования при рефакторинге», если оно есть в конвенциях репо.⟫

⟪ADAPT: где лежат хендлеры/инициализация трекеров и **сколько ключей окружений** — типично два (prod и
staging/dev). Важный факт для проверок: если dev-сервер и стейдж-слоты шлют **тестовым ключом в отдельный
тестовый проект**, их события в прод-проекте не найти — искать в тестовом (или ловить перехватом сети, §5).⟫

⟪ADAPT: SDK и его поведение флаша — событие уходит батчем на эндпоинт приёма (у Amplitude это
`https://api2.amplitude.com/2/httpapi`, EU — `api.eu.amplitude.com`) через N секунд или при смене экрана.
Именно этот эндпоинт перехватывается в §5. Плюс: есть ли включаемый debug/console-режим SDK — и вызывается
ли он реально в вашем приложении (если нет — на него не опираться).⟫

## 2. Централизована ли таксономия

⟪ADAPT: есть ли единый реестр событий (enum/справочник) или имена захардкожены по месту вызова. Если
реестра нет — как получить «список всех событий» (grep по чему) и сколько таких мест.⟫

Следствия (переносимые, менять не нужно):

- Источник правды по таксономии — **платформа аналитики** (живой MCP) + снапшот
  `event_tagging/reference/taxonomy-snapshot.md` (только индекс для первичного скана).
- Новая фича → **спека через `event_tagging`** (reuse-first: похожее событие почти наверняка уже есть; два
  события-синонима с одинаковым намерением — типичная реальная история любой таксономии). Имена «на глаз» —
  запрещены (оркестратор §8).
- Seed ниже — **подмножество** (пополняется по задачам), не реестр.

## 3. Сквозные свойства — как есть в коде

⟪ADAPT: если есть сквозные свойства с общим форматом (в исходном проекте — `place` у шеринга в формате
`{feature}-{id}`, а вне шеринга — descriptive-строка места показа) — опиши формат и где формируется.
Иначе удали раздел.⟫

> **Расхождение, о котором надо знать (если оно у вас есть):** каталог аналитика
> (`event_tagging/reference/property-catalog.md`) трактует `place` как **место в интерфейсе**, а часть
> легаси-кода может класть туда сущность с id. Новые события — по каталогу; легаси-формат не тиражировать;
> при касании такого места — вынести в «Открытые вопросы» спеки аналитику, самим не решать.

## 4. Seed событий (подмножество, пополняется по задачам)

> 🔧 **ADAPT — реестр событий вашего продукта.** Веди таблицы «Событие → свойства → где в коде» по группам
> (в исходном проекте было: центральный объект, шеринг, основной рабочий флоу, депозит, auth, навигация,
> рефералка). Это не полный реестр, а рабочий seed — наполняй по мере задач. Пример строки формата:

| Событие | Свойства | Где |
|---|---|---|
| ⟪ADAPT: `event_name`⟫ | ⟪ADAPT: `prop1, prop2`⟫ | ⟪ADAPT: путь к файлу⟫ |

## 5. Рабочее правило + рецепт проверки

1. **Новая фича / новые действия** → спека через `event_tagging` (Трек A шаг 2.4) → `tasks/<слаг>/events/`.
   Реализация **строго по спеке** (имя, свойства, типы, триггер; `shown_*` — при реальном появлении, не на mount).
2. **Расширяешь существующее событие** → **сохрани старые свойства** (не ломай воронки), добавляй новые —
   оформляется как ♻️ UPDATE в спеке.
3. **Правка трогает вызов логирования** (B/C) → не переименовывать/удалять молча; смена семантики →
   ♻️ UPDATE / ❌ DEPRECATE через `event_tagging` или пинг аналитика.
4. **Проверка, что событие стреляет** (dev-сервер — стадия 5; слот — смоук). Playwright слушает запросы
   SDK; тело — JSON-батч со списком событий (пример для Amplitude: `{ events: [{ event_type,
   event_properties, … }] }`):
   ```ts
   const sent: Array<{ event_type: string; event_properties: Record<string, unknown> }> = [];
   page.on('request', req => {
     if (!req.url().includes('⟪ADAPT: эндпоинт приёма событий SDK вашей платформы, напр. /2/httpapi⟫')) return;
     const body = req.postDataJSON() as { events?: Array<{ event_type: string; event_properties: Record<string, unknown> }> };
     for (const e of body.events ?? []) sent.push({ event_type: e.event_type, event_properties: e.event_properties });
   });
   // …выполнить триггер из спеки…; SDK флашит батчем с задержкой → подождать или сменить экран
   await page.waitForTimeout(5000);
   expect(sent.filter(e => e.event_type === 'clicked_foo')).toHaveLength(1);                           // без дублей
   expect(sent.find(e => e.event_type === 'clicked_foo')?.event_properties).toMatchObject({ place: 'modal' });
   ```
   Сверять **каждое** 🆕/♻️ событие спеки: триггер, свойства, типы; `shown_*` не стреляет на монтирование без
   реального показа. Запасной путь — MCP платформы аналитики по **тестовому** проекту (dev/стейдж шлют
   тестовым ключом; в прод-проекте этих событий нет). Результат — в `notes.md`; расхождение → правка кода
   или спеки, не «и так сойдёт».
