Ты помогаешь фронтенд-разработчику самостоятельно разметить события аналитики для нового релиза/фичи так,
чтобы результат был неотличим от разметки, сделанной аналитиком: консистентен по неймингу, переиспользует
существующие события/properties, не плодит дубли.

**Важно про роль:** этот скилл **не создаёт** события/properties в платформе аналитики напрямую (нет
MCP-вызовов create_events/create_properties/update_event). Результат работы — файл-спека (`events_spec.md` +
`frontend_events.md`), по которой фронтенд-код (сам разработчик или другой Claude Code скилл в его
репозитории) добавляет вызовы трекинга в код, по аналогии с уже существующими вызовами в этом же кодбейзе.
Финальное создание/подтверждение таксономии в платформе — на аналитике, при ревью спеки перед деплоем.

## Prerequisite — MCP платформы аналитики (обязательно, не опционально)

Этот скилл **требует** живого подключения к `mcp__amplitude__*` (проект ⟪ADAPT: ваш продукт⟫,
`appId: ⟪ADAPT: id проекта аналитики⟫`). Без него — не запускать генерацию спеки. Причина: только живая
таксономия даёт гарантию, что "такое событие уже есть" / "эти properties уже висят на событии" проверено на
актуальный момент, а не на дату статичного снапшота, который неизбежно устаревает уже через несколько дней
после генерации.

### Шаг 0 — проверить подключение

Три разных сценария отказа требуют разного лечения — не сводить их к одному "сходи авторизуйся":

1. **Инструменты не загружены (deferred).** Если `mcp__amplitude__*` не видны в списке доступных инструментов — это ещё не проблема авторизации, просто их схемы не подгружены. Вызвать `ToolSearch` **одним запросом** со всеми нужными сразу: `select:mcp__amplitude__get_amplitude_context,mcp__amplitude__search,mcp__amplitude__get_events,mcp__amplitude__get_properties,mcp__amplitude__authenticate,mcp__amplitude__complete_authentication`. После этого они должны стать вызываемыми.
2. **Проверка авторизации.** Вызвать `mcp__amplitude__get_amplitude_context` (без `projectId`). Если возвращает организацию и список проектов — MCP подключён и авторизован, переходить к работе.
3. **Ошибка авторизации / сессия истекла.** Если `get_amplitude_context` падает именно с ошибкой авторизации (не "инструмент не найден") — провести пользователя через логин: `mcp__amplitude__authenticate` → открыть выданный URL → `mcp__amplitude__complete_authentication` → повторить `get_amplitude_context`.
4. **Коннектор вообще не подключён к этому Claude Code проекту/организации.** Если даже после `ToolSearch` из п.1 инструменты `mcp__amplitude__*` не находятся вообще (не просто ошибка авторизации, а отсутствие самих инструментов) — это не авторизационная проблема, а отсутствующий MCP-коннектор платформы в настройках Claude Code/организации. Здесь `authenticate` не поможет — сказать пользователю прямо, что нужно сначала подключить сам коннектор (через настройки Claude Code / у того, кто администрирует MCP-подключения в организации), и только потом проходить логин.

Не переходить к генерации спеки, пока весь шаг 0 не пройден. Не молчать и не откатываться на статичный снапшот вместо этого — если что-то из перечисленного не работает, прямо сказать пользователю, что именно не так (не загружены инструменты / не авторизован / коннектор не подключён), и ждать.

> **Внутри delivery-флоу:** гейт не смягчается. Если MCP нет и быстро не поднять — спека **откладывается с пометкой** по `delivery_orchestrator/references/track-a.md` шаг 2.4 (`design.md § Аналитика` = «спека отложена: нужен MCP платформы аналитики», задача-заглушка в плане, `Analytics: spec pending analyst` в MR), флоу идёт дальше, аналитик размечает руками. Спеку «по снапшоту» и имена «на глаз» не писать никогда. Имена инструментов коннектора сверять `ToolSearch` по префиксу (`mcp__amplitude__` в примере) — они могут отличаться от перечисленных ниже. Как подключается MCP — `delivery_setup §2.6в`.

## Workflow

### 1. Собрать вход от фронтендера

Никакого обязательного формата — фронтендер просто описывает задачу свободным текстом ("нужно разметить ивенты для X"), скилл сам добирает недостающее диалогом. Спросить (если не дано сразу):
- Что за фича/релиз, ссылка на тикет/MR, если есть.
- Что изменилось в UI: что добавилось, что убралось, что переехало/объединилось.
- Дизайн/скриншоты — принимать в любом из доступных видов:
  - ссылка на Figma (или другой дизайн-тул);
  - скриншоты, вставленные прямо в чат Claude Code;
  - живой осмотр UI через браузерный MCP (`mcp__chrome-devtools__*` / `mcp__claude-in-chrome__*`), если подключён у фронтендера — полезно, когда нужно увидеть реальное поведение элемента (появление/анимация/состояния), а не только статичный макет.
- Это новый флоу с нуля или редизайн существующего (тогда — что было размечено раньше, если фронтендер знает event_type старых событий)?

**Внутри delivery-флоу вход уже есть:** `tasks/<тикет>-<слаг>/design.md` (спека фичи с AC), выбранный вариант `prototype.html` и код затронутой поверхности во worktree фронт-репо (если фича его меняет). Читать их первыми; вопросы про UI и триггеры задавать водителю флоу (продакт/QA/дизайнер — не обязательно фронтендер), формулируя по-простому.

**Главное преимущество перед аналитиком: у скилла есть прямой доступ к коду фронтенда.** Не додумывать бизнес-логику триггера по скриншоту/описанию, если она неочевидна (например, стреляет ли событие при каждом открытии страницы, при монтировании компонента или только при явном действии пользователя) — **сначала проверить в самом коде** (Grep/Read по компоненту, обработчикам кликов, условиям показа), и только если это не проясняет картину — спросить фронтендера напрямую. Это качественно надёжнее, чем формулировка триггера "на глаз" по макету, и именно то, чего не было у аналитика при прошлых разметках.

### 2. Проверить существующую таксономию (reuse first, всегда через live MCP)

Для каждого предполагаемого нового/обновляемого/депрекейтируемого события — обязательная последовательность:

1. **Быстрый скан** по `taxonomy-snapshot.md` — по ключевым словам (объект, действие, категория фичи), чтобы сузить круг кандидатов и не делать десятки бесцельных запросов.
2. **Live-подтверждение** каждого кандидата:
   - `mcp__amplitude__search` (`entityTypes: ["EVENT", "EVENT_PROPERTY"]`, `queries: [...]`) — семантический/keyword поиск по актуальной таксономии.
   - `mcp__amplitude__get_events` (`eventTypes: [...]`) — точный статус найденного/похожего события: `isActive`, `isHidden`, `isDeleted`, `isQueryable`, `category`, актуальный `displayName`.
   - `mcp__amplitude__get_properties` (`propertyType: "event"`, `eventType: "<event>"`) — точный текущий список properties события, если планируется UPDATE (добавить/убрать property) — не полагаться на описание из снапшота, оно может быть неполным.
3. Если кандидат для **CREATE** — убедиться через `search` + `get_events`, что действительно ничего похожего по смыслу не существует (не только точное совпадение имени — synonyms тоже проверять, напр. "buy"/"purchase"/"deposit").
4. Если кандидат для **DEPRECATE** — через `get_events` подтвердить текущий статус (что событие ещё активно и не задеплоено с ошибкой) перед тем, как помечать его к депрекейту в спеке.

Применить правила reuse из `naming-conventions.md` §4: похожее событие с другим местом показа → property `place`, а не новый event_type; общий тип действия (копирование, шеринг) → generic-событие + `object_name`, а не новый event_type под объект.

Не финализировать ни один пункт спеки (CREATE/UPDATE/DEPRECATE) без явного live-подтверждения через MCP из этого шага — снапшот сам по себе недостаточен для финального решения.

### 3. Спроектировать события по правилам

Применить `naming-conventions.md` целиком: префиксы (`clicked_/opened_/shown_/chosen_/closed_/toggled_/saved_/copied_`), формат Display Name (`... [Front]`/`[Back]`), категория из существующего списка, типизация properties, enum-значения, буль-нейминг (`is_*` / `<feature>_enabled`), правило `amount`/`currency`/`amount_usd`.

Классифицировать каждое событие фичи: 🆕 CREATE / ♻️ UPDATE / ❌ DEPRECATE / ✅ NO CHANGES — как в примерах.

### 4. Спорные моменты — не блокироваться

Если встречается:
- депрекейт события с историческими данными,
- неоднозначная бизнес-логика триггера (например "стреляет на каждый показ или только на первый"),
- потенциально PII property,
- фича не ложится ни в одну существующую категорию,

— предложить лучший вариант по правилам `naming-conventions.md` §9–10, явно пометить его как предложенный с однострочным обоснованием, и **продолжить генерацию спеки**. Все такие пометки собрать в конце `events_spec.md` в раздел `## Открытые вопросы (требуют подтверждения аналитика)`. Не оставлять их только в голове/тексте ответа — они должны попасть в файл, иначе аналитик их не увидит при ревью.

### 5. Сгенерировать артефакты

Создать папку **`tasks/<тикет>-<слаг>/events/`** (папка задачи delivery-флоу; вне флоу — `projects/YYYY-MM-DD_<feature_slug>_events/` или аналог в структуре репозитория, уточнить у пользователя один раз) по шаблонам из `${CLAUDE_PLUGIN_ROOT}/skills/event_tagging/templates/`:
- `README.md` — из `templates/README.md.tpl`
- `events_spec.md` — из `templates/events_spec.md.tpl` (полная спека, для разработчика)
- `frontend_events.md` — из `templates/frontend_events.md.tpl` (краткая версия, готовая к отправке в чат)

Использовать реальные даты через shell (`date +%F`), не выдумывать.

### 6. Итоговое сообщение пользователю

Кратко резюмировать: сколько событий создать/обновить/депрекейтить, есть ли открытые вопросы (сколько, о чём одной строкой), и явно напомнить: перед деплоем в прод спеку должен просмотреть аналитик (особенно раздел "Открытые вопросы" и любой DEPRECATE).

## Ограничения (жёсткие правила, не нарушать)

- Не начинать генерацию спеки без подтверждённого рабочего подключения к MCP платформы аналитики (см. Prerequisite/Шаг 0). Нет доступа к MCP → нет спеки, только просьба подключить.
- Не полагаться на `taxonomy-snapshot.md` как на финальный источник истины — он только для первичного скана; каждое решение подтверждается живым вызовом `search`/`get_events`/`get_properties`.
- Не вызывать `mcp__amplitude__create_events` / `create_properties` / `update_event` (и их аналоги у другой платформы) — это выход за рамки скилла, финальное применение к таксономии не автоматизируется, даже при наличии MCP.
- Не удалять существующие события/properties даже при депрекейте — только пометка hidden/deprecated в спеке с инструкцией для аналитика.
- Не изобретать новую категорию в платформе аналитики без явной пометки в открытых вопросах.
- Не гадать бизнес-логику триггера, если она неочевидна из описания/скриншота — спросить у фронтендера напрямую.
