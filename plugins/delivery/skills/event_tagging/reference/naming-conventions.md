# Event Naming Conventions — ⟪ADAPT: ваш продукт⟫

Эталон для разметки новых событий. Основан на паттернах таксономии ⟪ADAPT: ваш продукт⟫ и прошлых
разметках ⟪ADAPT: ссылки на ваши спеки⟫.

Если что-то в конкретном случае не покрывается этими правилами — не гадать, зафиксировать вопрос в
`## Открытые вопросы` итоговой спеки и предложить свой лучший вариант с пометкой "требует подтверждения
аналитика".

---

## 1. event_type (техническое имя события)

- `snake_case`, английский язык, без сокращений кроме общепринятых в проекте (⟪ADAPT: принятые сокращения вашей таксономии и те, что **запрещены** в новых событиях — оставлены только в исторических метриках⟫).
- Всегда начинается с глагола в прошедшем времени, обозначающего **тип действия**, а не объект:

| Префикс | Когда использовать | Примеры |
|---|---|---|
| `clicked_` | Явный клик по кнопке/ссылке/иконке | `clicked_<object>_button` |
| `opened_` | Переход/навигация — открылся экран, таб, оверлей **в результате действия пользователя** | `opened_<screen>_tab`, `opened_<screen>_selection` |
| `shown_` | Что-то появилось **не по прямому клику** (авто-триггер, показ после условия, A/B) | `shown_<block>`, `shown_<screen>_overlay` |
| `chosen_` | Пользователь выбрал значение из набора опций (дропдаун, карточки, список) | `chosen_<option>`, `chosen_<entity>_account` |
| `closed_` | Явное закрытие/дисмисс (крестик, кнопка "Отмена") — **не** для случаев, когда экран просто покидают навигацией | `closed_<block>` |
| `toggled_` | Переключение тумблера/чекбокса; property передаёт новое состояние | `toggled_<setting>` |
| `saved_` | Подтверждение/сохранение настроек (объединяет разные кнопки с одинаковым смыслом действия) | `saved_<form>_settings` |
| `copied_` | Копирование значения в буфер обмена | `copied_info` |
| `created_` / `completed_` | Backend-события жизненного цикла сущности | `created_<entity>`, `completed_<entity>` |
| `got_` | Приложение получило асинхронный статус/апдейт извне | `got_<external>_status` |

**Не использовать:** ⟪ADAPT: legacy-префиксы вашей таксономии, которые не тиражируем в новых событиях (в исходной таксономии в такой паре ещё и опечатка в одном из имён — такие имена не повторять, а не «выравнивать под них»)⟫. Для аналогичного смысла в новых событиях использовать `toggled_`/`saved_`/`opened_` в зависимости от семантики.

- Имя описывает **действие + объект**, без указания места/страницы, если это не критично для уникальности (место — через property `place`, см. §3).
- Перед тем как придумывать новое имя — обязательно проверить `taxonomy-snapshot.md`: похожее по смыслу событие почти наверняка уже существует (см. §4 "Reuse first").

## 2. Display Name

Формат: **Title Case** от слов event_type + суффикс источника:

```
<Title Case Event Name> [Front]   — событие шлёт фронтенд
<Title Case Event Name> [Back]    — событие шлёт бэкенд
```

Примеры: `Clicked Buy Button [Front]`, `Completed Order [Back]`, `Chosen Route [Front]`.

- `[Front]`/`[Back]` — обязательный суффикс, без исключений.
- Само название в Display Name без изменений порядка слов относительно event_type (просто капитализация + пробелы вместо `_`).

## 3. Category

- Значение поля `Category` в платформе аналитики **обязано** совпадать с одной из уже существующих категорий в `taxonomy-snapshot.md` (⟪ADAPT: список категорий вашей таксономии, напр. Onboarding, Authorization, Profile, …⟫).
- Новую категорию заводить нельзя без явного запроса аналитика — если фича не ложится ни в одну существующую, это спорный момент → зафиксировать в открытых вопросах, предложить ближайшую существующую как временный вариант.

## 4. Reuse first — не плодить дубли

Перед созданием нового event_type или property:
1. Искать в `taxonomy-snapshot.md` по ключевым словам (объект, действие, фича).
2. Если похожее событие есть, но с другим триггером/контекстом — предпочесть **добавление property** (например, `place`) существующему событию вместо нового event_type.
3. Если найден почти дубль по смыслу, но разный event_type (так уже бывало: два разных события с одинаковым намерением — «нажал кнопку депозита» и «нажал кнопку пополнения» — оставлены оба по историческим причинам) — **не повторять эту ошибку**: если у фичи уже есть подходящее событие, переиспользовать его, а не создавать очередной синоним.
4. Депрекейтить старое событие можно, только если оно **заменяется** новым 1:1 и это явно сказано в спеке (см. §7). Никогда не удалять физически (историчные данные).

## 5. Properties

- `snake_case`, типизация обязательна: `string` | `number` | `boolean` | `number | null`.
- Значения enum — перечислять явно в спеке (`method (string) — <вариант-1>, <вариант-2>, <вариант-3>`), даже если список неполный на момент написания ("…").
- Булевы свойства:
  - Общий случай: префикс `is_` (`is_recommended`, `is_repeat`, `is_manual`).
  - Исключение: если свойство названо в честь UI-настройки с собственным именем — можно `<feature>_enabled` — сохранять единообразие с существующим неймингом той же фичи.
- `number | null` — использовать когда property логически неприменимо при определённом состоянии (например `<feature>_amount: null`, если `<feature>_enabled = false`), а не пустую строку/0.
- Деньги: только `amount` (в локальной валюте) + `currency` + `amount_usd`. Никогда `amount_<токен>` или прочие валютно-специфичные имена.
- Переиспользуемые сквозные properties — см. `property-catalog.md`. Всегда проверять его перед тем как изобретать новое имя для типового смысла (место показа, id объекта, флаг рекомендации и т.п.)

## 6. Триггер (Trigger) — точность формулировки

- Формулировать максимально конкретно: что именно вызывает событие (клик по какому элементу, показ какого блока), а не общее "открытие страницы".
- `shown_*`/`opened_*` модалок и баннеров — явно указывать: "стреляет при реальном появлении блока, не при монтировании компонента" (частая ловушка: компонент может смонтироваться до того, как блок реально видим).
- Если один визуальный элемент встречается в нескольких местах интерфейса (баннер + модалка/боттомшит) — не создавать отдельные события на каждое место, использовать общее событие + property `place` (см. `example-specs/01_banner_and_modal_events.md`: `place: banner | modal`).
- Если кнопка объединяет несколько пользовательских путей с одинаковым смыслом действия (например "Save" и "Proceed" оба фиксируют настройки перед следующим шагом) — унифицировать в один event_type, не создавать по событию на кнопку.

## 7. Изменения существующих событий (UPDATE) и депрекейт (DEPRECATE)

- **UPDATE**: добавление/удаление property у существующего события — фиксировать явно, с причиной ("такой кнопки больше не существует в новом флоу").
- **DEPRECATE**: только если функциональность полностью заменена. В спеке указывать: чем заменяется, и что в платформе аналитики событие нужно пометить `hidden`/`deprecated`, **не удалять** (историчные данные).
- Любой депрекейт с историческими данными или неоднозначная замена триггера — по умолчанию помечать в спеке как "⚠️ предложено, требует подтверждения аналитика" и продолжать с предложенным вариантом (не блокироваться).

## 8. Кросс-платформенные и внешние обвязки

- Сквозные правила отправки — ⟪ADAPT: сквозные правила вашей аналитики (пример — «все события также отправлять в GA4»)⟫; стандартная заметка в каждой спеке (см. `## Notes` в шаблоне `events_spec.md`).
- События внешней attribution/marketing-обвязки (пример — AppsFlyer) — отдельная категория:
  - Помечать `*(⟪ADAPT: имя вашей attribution-платформы⟫)*` в спеке.
  - Явно указывать, если событие **не существует** в таксономии основной платформы аналитики — "implement in frontend only", "Does not exist in the analytics taxonomy".
  - Указывать флаг ожидания идентификации пользователя (`waitUser: true` в примере), если применимо — обычно для платёжных/конверсионных событий, где нужно дождаться подтверждения пользователя/сервера.

## 9. PII и чувствительные properties

- Не передавать в event properties: полные email/телефон, точные адреса/идентификаторы платежей без необходимости, произвольный текст, введённый пользователем (message body и т.п.).
- Если фича подразумевает передачу потенциально чувствительных данных — предложить безопасную альтернативу (например, `masked`/`hash`/булев флаг вместо значения) и пометить как "⚠️ требует подтверждения аналитика/security".

## 10. Что делать со спорными моментами

Правило по умолчанию (см. основной SKILL.md): **не блокироваться**. В каждом спорном случае:
1. Предложить конкретный вариант по правилам выше.
2. Явно пометить его как предложенный, с одной строкой обоснования.
3. Продолжить генерацию остальной спеки.
4. Собрать все такие пометки в раздел `## Открытые вопросы (требуют подтверждения аналитика)` в конце `events_spec.md` — единая точка для ревью аналитиком перед деплоем.
