# mobile-harness — стек, связка, грабли

Харнесс для QA нативного Android-приложения. `⟪ADAPT⟫` метит проектные значения.

## Архитектура (почему мобильный QA дёшев)

Приложение — **тонкая нативная WebView-обёртка над тем же web-client** (`⟪ADAPT: com.example.app⟫`;
может быть вторая сборка типа `⟪ADAPT: com.example.app.ai⟫` — обе ловят схему `⟪ADAPT: app://⟫`). Веб-бандл
едет **со слота стейджа**, не вшит в APK. Поэтому **«проверить ветку в приложении» = катнуть эту ветку
на слот** (обычный флоу), и навести приложение на него — без пересборки APK. APK меняется только когда
меняется *нативный шелл*; это и есть нативный MR (бридж/деплинк/хранилище/permissions).

Варианты сборки: **debug** (debuggable → CDP + `run-as`, смотрит на стейдж, нужен дев-VPN) и
**production-release** (release-подпись, НЕ debuggable → нет CDP/`run-as`, смотрит на прод → доступен без
VPN). Имя APK обычно несёт коммит (`…-<sha>.apk`) — сверь с головой MR
(`git merge-base --is-ancestor <mr-head> <build-sha>`). Over-install требует одинаковой **подписи** обеих
сборок (debug↔debug или тот же release-ключ), иначе `INSTALL_FAILED_UPDATE_INCOMPATIBLE`.

## Стек

| Слой | Инструмент | Зачем |
|---|---|---|
| UI-действия | **mobile-mcp** (`@mobilenext/mobile-mcp` в `.mcp.json`) | тап/скрин/запуск/список-девайсов/элементы. Надёжнее `monkey` для вывода на передний план |
| DOM/JS/сессия/консоль | **сырой CDP** (`cdp-recipes.md`) | Playwright `connectOverCDP` сломан на Chrome 150 |
| Нативка | `adb` + `logcat` + `dumpsys` + **`run-as`** (debug) | слепки хранилища при over-install, фокус-активити, wakelock, состояние permissions |
| Логин | temp-wallet API-минт + CDP-инъекция (`cdp-recipes.md §4`) | без ручного ввода; `../delivery_qa_smoke/references/auth-scenario.md` |
| Разбор диффа | read-only субагенты по блокам | нативный MR большой (100+ файлов) → карта «пункт чеклиста → код» |
| Юнит-тесты | `gradle` (верный вариант-таск, JDK по toolchain) | дешёвый первый сигнал до любого живого прогона |

## Связка (как складываются на одной проверке)

Типичная нативная проверка = **драйвить одним слоем, наблюдать другим**: вызвал метод бриджа через CDP →
смотришь нативный сайд-эффект через `dumpsys`/`logcat`/скрин; или послал деплинк через `adb am start` →
смотришь `set-deeplink` в `logcat` + durable-store через `run-as`. Тапы+скрины mobile-mcp — человеко-
видимый слой; CDP — источник истины по DOM/роуту; `run-as`/`logcat`/`dumpsys` — нативный слой. Временные
скрипты держи вне репозитория (скретч типа `.playwright-mcp/`, удаляй после).

## Эмулятор vs девайс

- **Эмулятор** — для покрытия API, которого не даёт девайс (пуш-промпт только API 33+, поворот/фолд на
  планшет/resizable AVD, Android 8.0/8.1 под класс краша permissions). На Apple Silicon — **arm64**
  образы; бут с `-gpu host` (софтверный GPU даёт ANR на холодном старте). Дотягивается до стейджа через
  хостовый VPN (NAT флакует — см. грабли). google_apis (без Play) → WebView не обновить.
- **Физический девайс** — реальное железо (камера, ощущение хаптики, реальные share-таргеты), стабильная
  сеть, WebView Play-обновляемый (современный) → SPA работает. Предпочтителен, когда загрузка стейджа на
  эмуляторе флакует.

## Логин и данные

temp-wallet (API-минт + CDP-инъекция) — по умолчанию; реальные аккаунты не трогать, UI-логин только для
теста самого логина. Отдай сминченный `USER_ID` пользователю, если проверке нужно состояние аккаунта,
которое ставит он (KYC-верификация, пополненный баланс). `pm clear` — чистый разлогин (cookie-сессия
переживает очистку localStorage).

## Грабли (каталог — читай до того, как воевать с тулингом)

1. **Debug-сборка доверяет только СИСТЕМНОМУ стору CA, не user-CA** (`network_security_config` разрешает
   лишь cleartext на localhost). Значит стандартный «поставить user-CA + прокси» НЕ работает — MITM/HTTPS
   требует **системного** CA. На API 35 APEX `bind-mount` стора `cacerts` виден только первому форку
   приложения и теряется при churn/ребуте → матрица экранов ошибок 5xx/4xx **требует рут/Magisk-системный
   CA**. Оставляй заметкой «нужен рут-стенд», в обязательный флоу не тащи.
2. **Старый WebView эмулятора (API 26/27 = Chromium 58/61, google_apis)** не парсит современный JS → SPA
   висит на сплэше; до веб-UI не дойти. Для нативного краша (напр. `PermissionsActivity.onCreate` падает
   на API 26/27, когда у прозрачной активити есть `screenOrientation`) запускай активити напрямую:
   `adb root` + `am start -n <pkg>/.<Activity> --es <REQ_ID_key> <v> --esal <PARAMS_key> <VAL>`.
3. **MIUI не ловит `adb input tap` по grid/RecyclerView** (системный файловый пикер) — кнопки и
   app-иконки ловятся, строки списка нет. Селекция через **DPAD**: `input keyevent DPAD_DOWN`/`DPAD_CENTER`.
4. **Две сборки обе ловят `⟪ADAPT: app://⟫`** → неквалифицированный деплинк открывает `ResolverActivity`.
   Целься явно: `am start -n <pkg>/.<Activity> …`. В шелле квотируй `&` и `"` в URL — **девайс**-шелл
   пере-парсит (`no closing quote`); обёртка `-d`-значения должна пропустить сырую `"`.
5. **Cookie-сессия не перебивается инъекцией localStorage** (соц-логин держится нативно) → `pm clear` для
   настоящего разлогина. temp-wallet — `mode:'cookie'` (сессия в cookie-store, не в localStorage —
   `hasCreds:false` там ожидаемо).
6. **CDP-форвард умирает при рестарте приложения** — сокет `webview_devtools_remote_<pid>`, PID меняется.
   Пере-резолви + пере-форвардь каждый раз (см. `cdp-recipes.md §0`).
7. **Эмулятор→стейдж через хостовый VPN-NAT флакует** (транзиентные сбои загрузки → корректно
   показывается нативный экран ошибки — это и есть доказательство для проверки экранов). Хост тянет
   стейдж стабильно (`curl` 200). Для стабильности гони на физическом девайсе либо ретрай.
8. **`am start` для `PermissionsActivity` и т.п.** требует `adb root` (не-exported активити); на
   release-сборке нет рута/CDP → используй dev-панель или девайс в руках пользователя.
9. **`monkey` ненадёжен для вывода на передний план** после `pm clear` → запускай через `mobile-mcp`.

Пополняй грабли тут каждую сессию — этот файл накопитель (durable — фиксируй в своих заметках/памяти).
