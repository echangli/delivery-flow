# release_notes — конвенции: текст, механика трекера, скрины

Справочник к скиллу `release_notes`. Не выводи формат из головы — сверяйся с этим файлом и с
1–2 последними выпущенными релизами на доске команды.

---

## 1. Структура текста (`tasks/<слаг>/release-notes.md`)

Пользовательский язык. Что получил пользователь — не как устроено внутри.

```markdown
# <Фича> — <короткий подзаголовок>

_<MR/ветка · стенд · desktop + mobile>_

<1–2 предложения сути: что теперь может пользователь>

## Что нового

- **<Название>** — <что появилось/изменилось, пользовательским языком>.
- …

## Границы

- <что НЕ вошло / где недоступно / ограничения>.

## Скриншоты

### Desktop
**<подпись>**
![<alt>](release-shots/<file>.png)

### Mobile
**<подпись>**
![<alt>](release-shots/<file>.png)
```

**Правила копи:**
- **Не выдумывать** — каждый пункт подтверждается design.md/диффом/notes. Сверяй с реальным диффом.
- **Пользовательский язык:** описывай эффект для пользователя, а не реализацию (не имена полей/файлов).
- **Без косметики рефактора и внутряка** — тех-детали вёрстки/кода в ноутс не идут, только то, что
  меняет пользовательский опыт.
- **«Границы» — обязательны.** Что НЕ вошло / где недоступно / чего нельзя. Управляет ожиданиями.
- Опц. прогнать новые строки исходной копи через ⟪ADAPT: плагин качества копи, если есть⟫ (advisory).

## 2. Релиз-трекер команды

⟪ADAPT: этот раздел — под ваш трекер (Notion / Confluence / GitHub Releases / вики). Ниже — пример
для Notion; если трекер другой, опишите его шаблон страницы и способ заполнения по аналогии.⟫

### Структура доски (пример: Notion Releases DB)
Страница релиза имеет свойства: `Name`, `Platform`, `Status` (черновик/выпущено), `Date`, `Releaser`.
Тело — по шаблону:

```
## Изменения
-
## Файлы
<file src=""></file>
```

Блок изменений — плоский маркированный список (пользовательские пункты). Блок файлов — картинки
(иногда пары в 2 колонки). Пустой плейсхолдер шаблона заменяем на картинки.

### Как заполнять (НЕ менять шаблон)
Заполнять **только** два блока: список изменений и блок файлов. **Заголовки и статус не трогать.**
«Что нового» + «Границы» из `release-notes.md` сливаются в единый список изменений.

**Сверься с 1–2 последними выпущенными релизами** перед заполнением — формат списка и раскладку
картинок держи как на доске.

### Найти/создать страницу
- Человек дал ссылку на созданную страницу → работать с ней.
- Иначе найти релиз-базу, создать страницу или попросить человека создать по шаблону и прислать ссылку.

### Загрузка скринов
Порядок **desktop → mobile**.

> 🔧 **ADAPT — механика загрузки под ваш трекер.** Пример для **Notion MCP**:
> 1. `notion-create-file-upload` (filename) → `upload_url` + `upload_headers` (Bearer) + `file_upload_id`.
> 2. POST файла на `upload_url` (окно ~5 мин): `curl -s -X POST "<upload_url>" -H 'authorization: Bearer
>    <token>' -F "file=@<path>.png;type=image/png"` → ответ содержит `markdown_source: file-upload://<id>`.
> 3. Вставить в тело блока файлов через `notion-update-page` (`update_content`): заменить
>    `<file src=""></file>` на строки `<image src="file-upload://<id>"></image>` в порядке desktop→mobile.
> 4. Проверить `notion-fetch` — картинки отрендерились.
>
> Заполнение списка изменений — тем же `update_content` (old_str→new_str): заменить плейсхолдер `-`
> под заголовком на маркированный список. Для другого трекера — своя механика (API/ручной ввод).

### Деградация (интеграция недоступна/не авторизована)
Не падать: отдать человеку готовый текст (Изменения/Границы) + список путей к скринам (в нужном
порядке) + короткую инструкцию: создать страницу по шаблону, вставить список в блок изменений,
приложить скрины в блок файлов. Подсказать, как подключить интеграцию. Секреты/токены — не в чат.

## 3. Скрины — чек-лист кадров

- **Кроп по изменённой области**, не весь экран (полноэкранные кадры — шум).
- **Две разные папки, не смешивать:** полноэкранные QA-кадры смоука живут в
  `tasks/<слаг>/screenshots/` (`NN-шаг.png`, мобильные `phone-`/`m-`) — из них берём **исходники**;
  релизные **кропы** для доски класть **отдельно** в `tasks/<слаг>/release-shots/` с префиксами
  `d-`/`m-` (desktop/mobile), напр. `d-01-<что>.png`, `m-00-<что>.png`.
- **Переиспользовать** уже снятое: есть кадр в `screenshots/` — кропнуть его в `release-shots/`,
  а не переснимать.
- Набор: ключевые поверхности фичи × {desktop, mobile} × значимые состояния (до/после,
  пустое/заполненное). Для сравнения — парные кадры.
- Автоснятие — только по запросу: процедура логина и стенда — `delivery_qa_smoke`
  (references `auth-scenario.md` / `test-data.md`). Готовые кропы — в `release-shots/`.
- В `release-notes.md` ссылаться на `release-shots/…`; в трекер — заливать их (§2).

## 4. Анонс в чат (опционально, не публиковать самому)
Простой стиль: заголовок «🎉 Релизнули <X>!» + 1 строка сути + короткий список пунктов «что нового» +
строка «Границы» + «работает на мобилке» если так. Отдать текст человеку — публикует он сам.

---

## 5. Чек само-проверки
- [ ] Черновик собран из реальных артефактов, сверен с диффом; не выдуман.
- [ ] Есть «Что нового» и «Границы»; язык пользовательский, без внутряка/косметики.
- [ ] Скрины — кроп, desktop+mobile, переиспользованы если были.
- [ ] Трекер: заполнены только изменения + файлы; шаблон и статус не тронуты; сверено с прошлым релизом.
- [ ] Картинки в порядке desktop→mobile, отрендерились.
- [ ] Без интеграции — корректная деградация (текст + список файлов + инструкция).
