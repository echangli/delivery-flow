# /release_notes — сборка релиз-ноутс по фиче/MR

Собрать релиз-ноутс по **одной фиче/MR** — пользовательским языком, со скринами, и заполнить страницу
в **релиз-трекере команды** (⟪ADAPT: где команда ведёт релизы — Notion / Confluence / GitHub Releases / …⟫).
Не тех-ченджлог, а «что получил пользователь» для внутренней релиз-доски.

**Когда:** после мержа (или на готовой ветке/MR). Explicit-invoke; delivery-флоу в финале мягко предлагает.

**Отличие от соседей:** `qa_mr`/`delivery_qa_smoke` — про качество (что проверить); `release_notes` —
про коммуникацию релиза (что и как рассказать). Копи-качество исходной копи — зона
⟪ADAPT: плагин качества копи, если есть⟫ (advisory-гейт).

Детальный формат текста, механика трекера (шаблон страницы, загрузка файлов, сверка с прошлыми
релизами), правила копи и чек-лист кадров — **`references/release-notes-conventions.md`**. Прочитай
его перед сборкой — не выводи формат из головы.

---

## 1. Когда запускать

- **Пост-мерж** — основной кейс: фича вмержена, нужно оформить релиз на доске.
- **На готовой ветке/MR** — можно собрать заранее (черновик), заполнить трекер после мержа.
- **Одна фича = один вызов = одна страница релиза.** Несколько MR/фич сразу → попросить сфокусироваться
  на одной (агрегированный ченджлог за период — не задача этого скилла).

Не мержит, не деплоит, **не меняет статус релиза на «выпущено»** — это человек.

---

## 2. Предусловия

### Интеграция с трекером (для заполнения доски)
Нужен подключённый и **авторизованный** способ писать в релиз-трекер:
⟪ADAPT: как команда пишет в трекер — MCP-коннектор (напр. Notion MCP), API-токен, или вручную⟫.
Проверка доступности — ⟪ADAPT: как проверить (напр. `claude mcp list` → коннектор `✓ Connected`)⟫.

**Если интеграция недоступна/не авторизована** — не падать: собрать `release-notes.md` + подготовить
скрины, отдать человеку готовый текст (Изменения/Границы) и список файлов + короткую инструкцию,
как вставить в трекер вручную; сказать, как подключить интеграцию.

### Скрины (опционально)
Кроп-скрины desktop+mobile для блока файлов. По умолчанию — **переиспользовать** снятые из
`tasks/<слаг>/screenshots/`. Автоснятие на стенде (логин + браузерная автоматизация) — **только по
запросу**; механика логина/стенда/деплоя — из `delivery_qa_smoke` (references auth-scenario / test-data).

---

## 3. Входы (приоритет)

Скилл определяет источник сам; **всегда сверяет черновик с реальным диффом**, чтобы не выдумывать.

1. **Папка задачи** `tasks/<слаг>/` — `design.md` (суть, scope, границы/non-goals, AC), `notes.md`
   (лог решений), `screenshots/` (готовые кадры). Основной и самый богатый источник.
2. **Ветка/MR** — дифф (`git diff origin/main...<ветка>` или API-compare для смерженной ветки),
   коммиты, MR title/description (API git-хоста ⟦GIT_HOST⟧).
3. **Явное описание** от человека — fallback и уточнения, когда нет папки/MR или фича неоднозначна.

Нет папки задачи → по MR/диффу; нет и MR → по описанию. Всегда сверять с диффом (что реально изменилось).

---

## 4. Шаги

### 0. Определить фичу и источник
Найти папку задачи / MR / описание. Прочитать `design.md` + дифф + `notes.md`. Уточнить у человека,
если фича неоднозначна или охватывает несколько MR (одна страница = один релиз).

### 1. Черновик текста (авто)
Собрать по фактам (design.md + дифф), **не выдумывая**:
- **«Что нового»** — список: что появилось, что изменилось в поведении. **Пользовательским языком**
  (что получил пользователь), без тех-внутряка, имён файлов и косметики рефактора.
- **«Границы»** — обязательный раздел из scope/non-goals/known-limits: что НЕ вошло, где недоступно,
  ограничения. Управляет ожиданиями.

Язык — язык релиз-доски команды (по умолчанию — язык пользователя). Структура файла — в `references`.

### 2. Правка человеком
Показать черновик — человек финальный редактор копи. Записать в `tasks/<слаг>/release-notes.md`.
Опц. копи-гейт ⟪ADAPT: плагин качества копи⟫ для новых строк (advisory, не блок).

### 3. Скрины
Составить **чек-лист кадров**: ключевые поверхности × {desktop, mobile} × значимые состояния
(пустое/заполненное/ошибка, если релевантно). Исходники — из `tasks/<слаг>/screenshots/`
(полноэкранные QA-кадры смоука); релизные **кропы** (по изменённой области, не весь экран) класть
**отдельно** в `tasks/<слаг>/release-shots/` (префиксы `d-`/`m-`), не смешивая с QA-кадрами.
Автоснятие на стенде — только если попросят
(процедура — `delivery_qa_smoke`; desktop ⟪ADAPT: вьюпорт, напр. 1440×900⟫, mobile
⟪ADAPT: вьюпорт, напр. 402×760⟫).

### 4. Трекер (если интеграция авторизована)
- **Найти целевую страницу:** человек дал ссылку на созданную страницу релиза → работать с ней; иначе
  найти релиз-базу и создать страницу (или попросить человека создать по шаблону и прислать ссылку).
- **Свериться с 1–2 последними выпущенными релизами** по формату — как оформлены список изменений и
  блок файлов.
- **Заполнить** блок изменений (единый список из шага 2: «Что нового» + «Границы») и блок файлов
  (скрины). **Шаблон не менять**, **статус не трогать**.
- **Загрузка скринов:** порядок **desktop → mobile**. Точная механика (для конкретного трекера) —
  в `references`.
- **Деградация:** интеграция не авторизована → отдать текст + список файлов + инструкцию вставки, не падать.

### 5. Отдать
Ссылка на страницу трекера + путь к `release-notes.md`. Предложить короткий **анонс в чат команды**
(простой стиль: «Релизнули X!» + список пунктов) — но не публиковать самому.

---

## 5. Правила (кратко; детали — references)

- **Не выдумывать** изменения — только из design.md/диффа/notes. Не тащить внутряк/косметику рефактора
  (анти-паттерн: тех-деталь вёрстки вместо пользовательского пункта).
- **Пользовательский язык.** Что получил пользователь, не как это устроено.
- **Скрины кроп** по изменённой области, не весь экран.
- **Трекер:** не менять шаблон, заполнять только блок изменений (списком) + блок файлов; статус не
  трогать; свериться с прошлыми релизами перед заполнением.
- **«Границы»** — обязательный раздел.

---

## 6. Связь с флоу

- **Explicit** `/release_notes` — вне авто-цепочки (как `qa_backend`): обычный delivery-флоу его не
  подтягивает автоматически.
- **Подсказка в финале:** `delivery_orchestrator` после мержа/раскатки мягко предлагает собрать
  релиз-ноутс через этот скилл.
