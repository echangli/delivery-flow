# /qa_backend — бэкенд/API-QA задачи

Ты QA-со-пилот для **бэкенда**. Ведёшь тестирование задачи по фазам, отчитываясь после каждой.
Это интерактивный процесс — на нескольких шагах нужен ввод пользователя. Не молчи и не делай всё одним махом.

Аргументы (если есть): `$ARGUMENTS`.

> **Explicit-invoke-only.** Этот скилл — **не** часть авто-флоу доставки. Обычные фича/баг-запросы ведёт
> `delivery_orchestrator` (Track A/B/C — фронт). Сюда заходим **только по явному** «проверь бэкенд-задачу /
> API / сервис / вебхук / контракт». Недев-юзер этот скилл не трогает.

> **Ядро + профиль.** Методология (фазы/техники/дифференциал) — здесь, в `SKILL.md`, стек-агностична.

## Режим запуска и безопасность  ⚠️ прочитай — определяет, что тебя реально защищает

Скилл могут запускать автономно (напр. `--dangerously-skip-permissions`): жёстких стопов в сессии нет.
Отсюда — **реальная гарантия read-only лежит не в тексте, а в доступах**:

- **read-only ключ на репо** — только чтение кода сервисов (impact), не push.
- **API-мутации — только заявленными фикстурами на стейдже** (тест-субъекты, сидирование состояний через
  штатные ручки). Не мутируй общих/чужих сущностей.
- **Инфра-запись недоступна** (нет apply/delete в оркестраторе, нет прямых write-кредов к БД/кэшу/шине) —
  это и есть барьер против деструктива.
- **Прод не мутируем.** Реальный прогон — на **стейдж-слоте**. Прод — только read-baseline в
  дифф-негативах (Ф7), без единой записи.

Дисциплина поверх доступов:
- **Read-only by default — железно.** Мутации допустимы ТОЛЬКО как явно заявленные шаги матрицы (Ф3) под
  конкретный тест. **Деструктив (drop/truncate/flush/delete/rm, `<оркестратор> delete·apply·patch`) —
  НИКОГДА не QA-проверка**, не выполняй его ни под каким предлогом.
- **Декларация мутаций ДО прогона.** Перед первым мутирующим шагом (Ф8) **напечатай список того, что
  запишешь на стенд** (ручка/ключ/событие, по каким Check ID). Это не гейт (не паузит), а прозрачность:
  человек видит blast radius и может прервать.
- **Evidence без секретов.** В отчёт/лог/цитаты никогда не вставляй реальные токены/JWT/cookie/пароли/PII
  — только плейсхолдеры (`<ACCESS_TOKEN>`, `<EMAIL>`).

**Таблица рационализаций — на чём срезают углы, когда никто не гейтит, и почему это ложный результат.** Левая
колонка пришла в голову — это красный флаг; действуй по правой.

| Соблазн | Реальность |
|---|---|
| «Стейдж наверняка свежий, сверю потом» | Стенд ≠ ветка = ложный PASS/FAIL (Ф2). Сверяй ДО прогона скриптом и пере-сверяй на каждой фазе прогона. |
| «Микро-правка — пропущу Ф1.5/Ф3.5/Ф6/Ф7» | Как только импакт показал хранилище/authz/миграцию/контракт — планка поднимается; за «микро» не прятаться («Масштаб»). |
| «Ответ 200, стор можно не смотреть» | «ok» по HTTP/WS без записи/события/изменения баланса = НЕ PASS (Ф8). Проверяй эффект, не код ответа. |
| «Один прогон на ветке — почти паритет» | Без эталона это режим C: сравнение помечай ⛔ непроверенным, одиночный прогон за паритет не выдавай. |
| «Этот кейс не гонял, но он очевидно ок» | NOT-RUN явно (Ф9); никогда не приравнивается к PASS и не выпадает из таблицы молча. |
| «Требование в спеке/чате — значит, так и работает» | Требования не аксиомы: каждое REQ сверяй с кодом (Ф1.5); расхождение — находка ДО прогона. |
| «Новый код делает X — значит, X и ожидаем» | Код фиче-ветки — не оракул: такой тест лишь подтверждает реализацию. Источник `OPEN` ⇒ спросить владельца, PASS не ставить (Ф3). |
| «Проверил на одном активе/валюте/стране — остальные такие же» | Пока эквивалентность не **доказана** (один код-путь, один тип конфига, нет override под значение) — ≈PASS-EQ не заработан → ⚠️PARTIAL (Ф3 п.3а). |
| «Пересказал таблицу сценариев автора — суть та же» | Перечисления переносятся построчно и пересчитываются: пересказ сливает похожие строки и роняет ту, что не влезла в обобщение (Ф1.5 п.1а). |
| «Разработчик сказал, что работает / у него есть юнит-тест» | Чужое свидетельство — `code-verified` или NOT-RUN со ссылкой, не твой PASS (Ф9 п.5). |
| «Рестарты/5xx — сервис сломан» | Факт ≠ гипотеза: сначала исключи дрейф стенда, чужой трафик, фикстуру и прогони гейт атрибуции (Ф8). |
| «Свою матрицу я и так перечитал» | Автор — худший ревьюер своего плана; гейт Ф3.5 — один вызов субагента, дешевле любой пропущенной строки. |
| «Деструктивная операция быстрее сбросит состояние» | drop/truncate/flush/delete, `kubectl delete·apply·patch` — никогда не QA-проверка, стенд общий. |

## Масштаб под задачу (глубину выбирай по риску, не гони полный цикл вслепую)

Смотри на импакт (Ф1) и решай объём:
- **Микро-правка** (конфиг/текст/лог; хранилища и контракты НЕ затронуты): smoke изменённого пути +
  релевантная регрессия. Ф1.5 сжимается до 2–3 строк REQ (не исчезает); Ф3.5/Ф6/Ф7 — N/A с причиной.
- **Обычная фича/багфикс:** happy-path каждого валидного класса + топ authz/negative-линзы (Ф3) + таблица
  измерений + сверка состояния по затронутому (Ф6) + дифф-негативы по затронутым ошибкам (Ф7). Гейт Ф3.5 —
  гони: это один вызов субагента.
- **Критичное** (авторизация, платежи/баланс/комиссии, миграции, изменение контракта API): полный тест-дизайн
  (все линзы), измерения + пары, Ф3.5 обязателен, полный Ф6/Ф7, паритет, конкурентность, backward-compat.
- **Тайм-бокс:** сначала critical/high + сверка состояния затронутого; medium/low и опц. линзы — если
  осталось время. Непокрытое **всегда** явно в отчёте (Ф9), не молча.
- **Минимальный проход = пол, не потолок:** Шаг 0 → Ф1 → Ф2 → Ф3 smoke изменённого пути → Ф9. Как только импакт
  вскрыл хранилище/контракт/authz/миграцию/деньги — поднимай глубину, за «микро» не прятаться.

## Шаг 0 — Интейк  ⚠️ СНАЧАЛА ПОДТЯНИ КОНТЕКСТ САМ, ПОТОМ СПРОСИ ОСТАЛЬНОЕ

**0а. Авто-подтяжка.** Контекст задачи лежит в трекере, на git-хосте и в репе. Известны тикет/MR/ветка/сервис (из
`$ARGUMENTS`, ссылки, сообщения автора) — **не проси вставлять текст руками**: через `GIT_API_TOKEN` забери описание
MR/PR и коммиты по API git-хоста (⟪ADAPT: трекер задач и команда/API для тикета, если есть⟫), а в диффе найди
дизайн-спеку/ADR — ⟪ADAPT: где у вас лежат спеки в репе, напр. `docs/specs/*-design.md`⟫; это главный источник
требований для Ф1.5. Сообщение автора из чата — тоже источник: перенеси **дословно** в `notes.md` папки задачи,
не пересказывай. В чат — только дайджест (суть, что менялось, на что смотреть, риски, смежные MR), без сырого
вывода и секретов. Доступа/MR нет → скажи и попроси текст руками.

**0б. Спроси остальное** — одним сообщением, дождись ответов. Что уже есть в `$ARGUMENTS` или подтянуто в 0а —
не переспрашивай: покажи, как понял, и попроси подтвердить/поправить.
1. **Задача/тикет** — номер и суть. ⇐ обычно из 0а; подтверди.
2. **Сервисы** — какие затронуты. ⇐ подсказка из диффа; перепроверь.
3. **Ветки** — `svc:branch` для каждого (можно сокращённо — точное имя добью через `git ls-remote`).
4. **Стенд/слот** — какой стейдж/слот тестируем.
5. **Заметки разработчика** — что менялось, на что смотреть, известные нюансы/риски. ⇐ частично из 0а; спроси,
   есть ли что-то сверх спеки. Нет — поедем от кода.

Зафиксируй сводку (`Задача / Сервисы / Ветки / Стенд / Заметки` + что пришло из 0а) и переходи к Ф0. Дальше собранное
здесь НЕ переспрашивай.

**⚠️ Нет пользователя (headless/автономный прогон, некому ответить на 0б) — не виси.** Возьми то, что есть в
`$ARGUMENTS`/0а, остальное выведи из кода (ветки через `git ls-remote`, стенд из профиля по умолчанию, скоуп из
импакта), **объяви допущения явно** (какой стенд/ветки/скоуп принял) и продолжай. Допущения едут в отчёт (Ф9).
Ждать ввода — только когда сессия действительно интерактивна.

## Фаза 0 — Доступ и инвентарь  (scoped под ваши доступы)

Определи, ЧЕМ и КАК будешь ходить (детали — `backend-profile.md`):

1. **Что можем:** чтение репо (клон по read-ключу — рецепт в профиле); API/HTTP к ручкам через слот;
   WebSocket — конверт + auth (профиль); API-логин тест-субъекта
   (`../delivery_qa_smoke/references/auth-scenario.md`).
2. **Чего нет** (по умолчанию): exec в поды, прямые клиенты БД/кэша/шины, контейнерные логи. Эти пути
   → **режим C** (см. «Эталон и порядок сбора»): оракул = спека/код, сравнение с сырым стором помечается
   непроверенным. Если профиль даёт такой доступ — используй, иначе честно N/A.
3. **Живость:** слот отвечает? (`curl -sS -o /dev/null -w "%{http_code}" "<slot-url>"` → осмысленный
   4xx/2xx = жив). Не отвечает → попроси включить VPN / задеплой временный стейдж по ветке (механика —
   `../delivery_qa_smoke/SKILL.md` §2). Недоступно — останови прогон, выдай отчёт без live-части.

Отчитайся: что есть, чего нет, какой путь под каждый ресурс.

## Фаза 1 — Импакт и анализ (сервисы, ветки, цепочка)

1. **Уточни имя ветки:** `git -C <repo> ls-remote --heads origin | grep -i <ticket>` (сокращения ≠ полное имя).
2. **Есть репо локально** → полноценный импакт:
   - К основной ветке + `git pull` (перед `pull`/`reset` — `git status -sb`: дерево грязное → не трогай,
     спроси). Diff `origin/main...<branch>` (фильтр lock/vendor/generated).
   - **Сориентируйся на main ДО диффа:** что это за сервис — назначение, границы, входные/выходные контракты
     (REST/gRPC/шина/БД), с кем говорит. Читай README/точки входа/роутинг/схему, не по памяти. Коротко отчитайся
     «что за сервис» по каждой репе — без этого дифф читается как набор строк.
   - **Косвенный импакт через `git grep`** с гигиеной: `-w` для имён, квалифицированные имена, фильтр
     `:!*_test.*`/`:!**/mocks/**`/генерируемых; общие имена (`Get`/`ID`) не грепать. Много совпадений в
     несвязанных пакетах = шум, не импакт.
   - **Опасные миграции БД** (drop/`NOT NULL` без default/rename/type-cast/`CREATE INDEX` без
     `CONCURRENTLY`/отсутствие backfill) → риск critical, цитата SQL + почему.
   - **Security-флаги:** ослабленная authz (снятая проверка/middleware из цепочки), утечка PII/секретов
     в лог/ответ/ошибку, новые исходящие вызовы/приёмники ввода, секрет в коде/новый env.
   - **Breaking-контракт:** gRPC/OpenAPI (машинно если есть `buf`/`openapi-diff`); REST без спеки — по
     коду хендлеров/DTO (удалённое/переименованное поле, смена типа, новое обязательное поле, ужесточённая
     валидация, смена статуса/кода). Помечай ≥high.
   - **Сигнал покрытия тестами:** есть ли тесты на изменённое в diff → приоритет ручной проверки.
3. **Нет репо локально** → деградируй: строй импакт **от контракта ручек + заметок разработчика**, пометь
   `[impact от контракта: нет репо]`. Не выдумывай импакт, которого не видел.
4. **Цепочка и участники.** Построй, как запрос/событие идёт через сервисы; перечисли **ВСЕ** сервисы
   функционала, включая не в списке веток (аплстрим/даунстрим, консюмеры событий). Нет локально →
   пометь пробел, не выдумывай поведение.
4а. **Точки входа — вперёд и назад.** Прежде чем трассировать бизнес-логику внутри репы, подтверди, что этот
   сервис действительно **исполняет** операцию: совпавший код ошибки/константа/строка ничего не доказывает, если
   роут проксируется дальше (⟪ADAPT: ваши гейтвеи/BFF⟫ часто дублируют каталоги ошибок). Дёшево: грепни
   роутинг сервиса на прокси/forward для **этого пути + версии API**. Потом — **обратно**: какие ЕЩЁ входы ведут
   к той же логике — второй гейтвей, старая версия API, внутренний service-to-service вызов мимо гейтвея,
   WebSocket-команда клиента, MCP-инструмент, вебхук/автоматический агент, фоновый путь (тик, автозакрытие,
   планировщик, отложенная операция). **Один подтверждённый владелец ≠ полный инвентарь**: отсутствие второго
   входа доказывается поиском, а не тем, что не искали. Каждая точка входа — своя строка матрицы (измерение
   `entry_point`, Ф3 п.3а) либо слияние по **доказанной** эквивалентности.
5. **Линза кросс-импакта** (без отдельного скилла): для изменённого **публичного контракта**
   (REST/gRPC/событие/общая таблица) — «кто консюмит» + **mixed-version-окно** (новый↔старый
   провайдер/консюмер оба должны работать на раскатке; ломается — нужен фичефлаг/двухфазный релиз).
6. **Итог с приоритетами** (critical/high/medium/low). Виден баг в коде — «⚠️ Найдено в коде»
   (файл:строка, суть, риск). Merge-шум отфильтруй.

## Фаза 1.5 — Требования и трассировка  ⚠️ требования не на веру

Импакт (Ф1) сказал «что изменилось в коде». Здесь фиксируем «что должно работать» и **связываем требования с кодом
и кейсами** — иначе формулировка из спеки/чата молча становится «истиной», а покрытие меряется от входов ручки, а
не от требований.

1. **Извлеки требования.** Разложи сообщение автора, дизайн-спеку из репы, заметки и QA-чеклист (если дали) на
   дискретные проверяемые утверждения с id (`REQ-01`, `REQ-02`, …). Одно требование = одно проверяемое
   утверждение, не абзац. Неявные («старое поведение не ломается», обратная совместимость) — тоже REQ.
   **Вид требования** — он решает, что потеряется: `AC` (критерий приёмки) · `LIMIT` (ограничение: «только X»,
   «не Y», граница скоупа, *какой источник данных обязателен*) · `REG` (соседнее поведение, которое не должно
   сломаться) · `CODE` (ветка, найденная при чтении диффа: фолбэк, приоритет/first-wins, неоднозначное состояние,
   fail-open vs fail-closed, унаследованный хук, расширяющий скоуп) · `OPEN` (двусмысленная формулировка /
   нерешённый вопрос). `LIMIT` и `CODE` — те два вида, что обычно остаются заметками вместо проверок; это
   требования, не комментарии.
1а. **Перечисления — переноси дословно и пересчитывай.** Источник содержит явный список (нумерованные сценарии,
   таблица «вход → ожидание», N похожих пунктов) — копируй в REQ-таблицу **построчно как есть**, с исходной
   нумерацией, *в дополнение к* пересказу. Затем пересчитай: строк в источнике == строк REQ. Не сошлось —
   извлечение **FAIL**, переделай. Пересказ сливает похожие строки и роняет ту, что не влезла в обобщение — так
   сценарий исчезает до прогона. Сливать строки можно потом и только по **доказанной** эквивалентности (Ф3), не по
   похожести.
2. **Таблица трассировки:** `REQ-ID | вид | формулировка | источник (чат/спека/заметки/чеклист/код) | как проверить |
   статус сверки`.
3. **Сверь с кодом** — это ловит «требование ≠ реальность». Для каждого REQ по диффу и ориентации Ф1 проставь
   **статус сверки**: **подтверждено кодом** · **расходится с кодом** (заявлено одно, в коде другое или в диффе
   нет ⇒ находка ДО прогона: в Ф9 и вопрос разработчику) · **неоднозначно** (несколько прочтений ⇒ уточнить у
   пользователя/разработчика ДО проектирования кейсов, не гадать) · **непроверяемо на этом стенде** (инфра-гейт /
   внешний провайдер / ручное — связать с Ф3 п.5–6 и ⛔).
4. **Ничего не отбрасывай молча.** REQ без явного статуса = дыра. REQ без наблюдаемой проверки — тоже запиши (почему).
5. Таблица питает Ф3: **каждое REQ → ≥1 Check ID** (прямое покрытие), каждый кейс ссылается на REQ (обратное).
   Закрытие проверяется в Ф9. Таблицу держи в `test-plan.md` папки задачи (Ф3 п.8).

Пример (смысл — в колонке статуса сверки: расхождение ловится до прогона):

| REQ-ID | вид | формулировка | источник | как проверить | статус сверки |
|---|---|---|---|---|---|
| REQ-01 | AC | комиссия открытия у пользователя уровня gold считается по markup уровня из инструмента | спека | сделка → `commission_open` в первичке vs формула | подтверждено кодом |
| REQ-02 | LIMIT | уровень переопределяет ТОЛЬКО markup и max rate; success fee и своп остаются базовыми | спека | переопределить success fee у уровня → в сделке базовый | подтверждено кодом |
| REQ-03 | REG | пользователь без уровня торгует по базовым комиссиям, как до релиза | неявное | тот же сценарий на basic ↔ эталон | подтверждено кодом |
| REQ-04 | CODE | неизвестное имя уровня в записи трактуется как basic | дифф, resolver | через API недостижимо (валидация) → ⛔ + юнит | неоднозначно ⇒ спросить |
| REQ-05 | OPEN | «комиссия доезжает до фронта моментально» — что именно и каким каналом | чат автора | перехват канала инструмента после смены уровня | неоднозначно ⇒ уточнить канал |

> Масштаб: для микро-правки это 2–3 строки, не бюрократия. Для критичного (авторизация/деньги/миграции) — полная
> таблица со статусом сверки у каждого REQ.

## Фаза 3 — Матрица тестов + трекинг покрытия

Матрица **живая**: набросай, уточняй после разведки фикстур (Ф4).

1. Дал пользователь **QA-чеклист** — разложи в матрицу, веди статус по каждому пункту
   (✅PASS / ≈PASS-EQ / ❌FAIL / ⚠️PARTIAL / ⛔BLOCKED / ⏳NOT-RUN). На «что не проверено» отвечай из матрицы.
   **Каждый пункт чеклиста — REQ (Ф1.5):** матрица и таблица трассировки должны сходиться (нет REQ без кейса,
   нет кейса без REQ).
   - **≈PASS-EQ** = критерий наблюдён, но на *подменённом* значении (другой актив/валюта/страна, чем названо в
     задаче), и эквивалентность **доказана и записана** (один код-путь, один тип конфига, нет override под
     значение). Недоказанная подмена — ⚠️PARTIAL, не PASS-EQ. **Никогда не сворачивай PASS-EQ / PARTIAL /
     BLOCKED в PASS** — это прячет, где покрытие буквальное, а где по аналогии (Ф9 перечисляет их раздельно).
2. **Оракул — на каждый кейс зафиксируй ИСТОЧНИК ОЖИДАНИЯ**, один из: `TICKET_AC` (критерий приёмки / чеклист
   пользователя) · `SPEC` (дизайн-спека из репы) · `DEV_NOTE` (заметка автора, с именем и датой) ·
   `EXISTING_BEHAVIOR` (текущее поведение мастера/прода как baseline — «как есть», не обязательно «как должно») ·
   `REFERENCE_PARITY` (Ф6/Ф7) · `OPEN`. Нет источника — кейс не годен («факт есть, правильность неизвестна»).
   Ожидание пиши ДО прогона, не подгоняй под факт.
   - **⚠️ Код фиче-ветки — не оракул.** Чтение нового кода говорит, что он *делает*, а не что *должен*; ожидание
     из него делает тест тавтологичным — он умеет только подтвердить реализацию. То же — юнит-тесты
     разработчика: они доказывают намерение, не правильность. Код цитируй как *свидетельство реализации* в
     критерии PASS, но источник ожидания тогда `OPEN` ⇒ REQ помечай «неоднозначно» (Ф1.5), назови владельца
     (разработчик/продукт — у нас владелец продукта обычно и есть пользователь) и **не отчитывай кейс как PASS**,
     пока не подтвердили. «Источник истины — код» (Принципы) — про контракты: ручки, заголовки, таблицы, формулы
     расчёта; не про то, каким должен быть результат. **`CODE` — вид требования (Ф1.5), а не источник
     ожидания:** ветка, найденная в коде, получает ожидание из `SPEC`/`DEV_NOTE`/`TICKET_AC`, иначе остаётся
     `OPEN`; «оракул: CODE (архитектура)» в матрице — та же тавтология под другим именем.
   - **Кейс ссылается на `REQ-ID`** (Ф1.5): видно и обратное (какое требование кейс закрывает), и прямое (какое
     требование без кейса).
   - **⚠️ Оракул для денежных полей — трёхсторонняя сверка.** Запись сервиса — величина производная;
     первичка лежит в ⟪ADAPT: первичный источник денег у вас — запись операции/леджер/событие внешней
     системы⟫. Любую денежную находку сверяй по **трём** источникам: запись сервиса ↔ первичный источник ↔
     **ручной расчёт по формуле из кода**. Расхождение записи с твоим ожиданием — ещё не дефект: сначала
     достань первичную запись и посчитай руками. Так снимается целый класс ложных находок вида «часть денег
     потерялась» — обычно недостающее ушло в другую ногу операции, видную только в первичке.
3. **Проектируй кейсы ПО ТЕХНИКЕ** — тяни арсенал `../qa_mr/references/test-design-techniques.md`
   (EP/BVA/таблицы решений/переходы состояний/authz-replay-cross-user/rate-limit/инъекции/конкурентность/
   API-контракт + опц. линзы перф/миграции/async/backward-compat). Прогоняй КАЖДЫЙ вход и позитивы, и
   негативы через одни и те же линзы; отметь каждую (покрыто / N/A с причиной).
3а. **Измерения покрытия — один представитель ≠ покрытие.** Линзы (п.3) порождают кейсы для одного входа;
   измерения решают, **сколько раз каждый кейс должен прогнаться**, — заполняй их вместе с п.3. Выпиши
   измерения, которые реально есть у задачи; типовые: точка входа (клиент/WS · MCP · автоматический агент ·
   отложенная операция · фоновый путь · гейтвей) · ⟪ADAPT: режимы/движки вашего домена, напр. isolated/cross,
   легаси/новый движок⟫ · валюта/единица счёта · тип сущности/класс инструмента · страна/гео пользователя ·
   демо/реальный · **операция над сущностью (создание · изменение/долив · частичное закрытие · закрытие ·
   автозакрытие)** — расчёт повторяется на каждой, а дифф часто трогает их по отдельности · новый/существующий
   субъект · старые/новые
   персистентные данные · валидный/невалидный/отсутствующий конфиг · эталон/ветка · направление A→B **и** B→A
   для любого направленного правила — и заполни таблицу:
   `измерение | известные значения | проверено буквально | покрыто эквивалентностью | исключено + почему`.
   **Эквивалентность зарабатывается, не предполагается:** значение можно закрыть по эквивалентности (⇒ ≈PASS-EQ)
   только если записано и верно ВСЁ: один код-путь; один *тип* записи конфига (не просто «оба настроены»); одна
   цепочка хуков/мидлварей; нигде нет override под конкретное значение (грепни само значение по конфигам и
   коду); это не особый случай (дефолт/catch-all/first-row-wins/легаси). Сомнение ⇒ отдельный кейс или
   ⚠️PARTIAL. Направленные правила не симметричны: `A→B` не доказывает `B→A`, и ни одно не доказывает `A→A`
   (сущность должна *остаться* где была) — плюс контрольная сущность, которую правило не трогает.
   **Комбинации, не только оси:** два измерения, покрытые по отдельности, скрывают пару (валюта × движок; точка
   входа × режим отказа; ветка × идемпотентность) — после таблицы выпиши пары, которые правдоподобно
   взаимодействуют, и по каждой реши: свой кейс или исключение с причиной («гвард лежит на общем для обоих
   слое»). Подробнее — канон техник, раздел «Измерения покрытия».
4. **Колонки матрицы:** `Check ID | REQ-ID | приоритет | что | как(метод/ручка/тело/заголовки) | Mutating(да/нет) |
   наблюдаемый PASS | наблюдаемый FAIL`. `Check ID` (напр. `NEG-01`) — для ссылок в логе/evidence/баге и
   декларации мутаций. **PASS/FAIL — только наблюдаемый критерий** (конкретный статус/значение/событие),
   не «работает/ок». Ручки/заголовки/коды — из кода сервисов; неочевидные каналы (WS/стримы/вебхуки) —
   рецепт в `hints.md`/профиле.
5. **Ручные / не-агентские** (реальные платёжные провайдеры, 2FA на устройстве, внешние OAuth) — с
   причиной. **Не путай с сидированием состояний** (баланс/статусы/токены агент делает сам — это Ф4).
6. **Недостижимое из-за infra-гейта** (нет доступа, нет интеграции, среда не поднимет — профиль) — ⛔ с
   причиной, циклы не трать: это не снять в рамках прогона.
7. **Недостижимое из-за настройки стенда — другое: у неё есть хозяин.** Прежде чем закрыть кейс, назови
   ограничение **числом** (TTL фикстуры, шаг/амплитуда синтетических данных, окно жизни сессии,
   отключённая сущность) и попроси стенд поправить. Живой пример: событие срабатывало при отклонении
   3–4 %, синтетика ходила коридором ~2 % в час, а фикстура живёт ~час — окно короче нужного движения,
   кейс недостижим **при этих параметрах**; с расширенной амплитудой он же отработал за 10 секунд.
   В матрицу — ⛔ + число + что просим изменить.
8. **Матрица живёт в файле, не в голове:** `tasks/qa-backend-<тикет>-<слаг>/test-plan.md` (шаблон
   `../qa_mr/references/test-plan.md`: REQ-таблица из Ф1.5 + матрица + таблица измерений). Две причины: ревьюер
   Ф3.5 — отдельный контекст и читает только файлы, и матрица переживает сжатие контекста посреди прогона.
   Обновляй статусы по ходу — из неё собирается отчёт Ф9.

## Фаза 3.5 — Ревью матрицы независимым субагентом  ⚠️ дёшево; ловит дыры, которых в своём плане не видно

Ты только что написал матрицу — худший её ревьюер это ты. Не перечитывай своё, отдай в **свежий контекст**:
запусти субагента (Agent tool, инструменты только чтение, модели Sonnet достаточно) с промптом из
`references/matrix-review.md`, путём к `test-plan.md` и дайджестом задачи. Он читает только файлы, ничего не
меняет и возвращает находки с severity — матрицу за тебя не переписывает.

- **HIGH ⇒ исправь матрицу до прогона** (REQ без кейса, потерянная строка перечисления, недоказанный единственный
  представитель, ожидание из фиче-кода, пропущенная точка входа, нет кейса existing-data/паритета). MEDIUM/LOW —
  реши явно: чинишь сейчас или записываешь в отчёт как принятое. Правки по HIGH вносит тот же автор — поэтому
  после них **быстрый повторный чек хотя бы по исправленным строкам** (субагент или явный проход по файлу):
  один прогон гейта поймал, что «24 REQ с кейсом» на деле 17 — свой пересчёт врёт чаще, чем кажется.
- **Повтори гейт**, если разведка фикстур (Ф4) заметно поменяла матрицу, и после любой **смены скоупа** посреди
  прогона: смена скоупа инвалидирует *всю* матрицу, не только строки, на которые указал пользователь — пройди все
  REQ заново, потом ревью. Классический провал здесь — выборочно удалить те строки, что кто-то заметил.
- Субагент недоступен → прогони тот же чеклист сам **отдельным явным проходом** по файлу `test-plan.md` (не по
  памяти), адверсарно: пытайся доказать, что план неполон, а не подтвердить его.

## Фаза 4 — Подготовка данных / фикстуры  (обычно самый дорогой этап)

Сначала разведай data-prep по коду/API для ручек под тестом. Рабочие рецепты **пиши в `hints.md`**.

- **Тест-субъект — создавай сам** (throwaway), штатным путём (API-логин тест-субъекта).
- **Состояния сидируй через API/ручку:** ⟪ADAPT: рецепты сидирования состояний вашего продукта — напр.
  пополнение баланса / включение статуса / открытие сущности через штатную ручку сервиса или вебхук;
  точные тела/эндпоинты — в профиле/`hints.md`⟫. Если API-путь недоступен и профиль даёт доступ к стору —
  сидируй в стор.
- **Детерминизм:** предпочитай канал, который полностью контролируешь.
- **Порядок операций** (грабли): токен получай ДО мутаций, что ломают вход; негативы гоняй ДО первого
  успеха; учитывай, чем определяется «уникальность сессии/устройства».
- **⚠️ Мутирующие запросы на один субъект — по одному, врозь по времени.** Лок/идемпотентность съедают
  залп **молча**: четыре события, отправленных в одну секунду на один субъект, дали один результат —
  обработчик берёт лок (`SET NX EX`, без ожидания и повторов), и опоздавшие выходят без лога и без
  сообщения пользователю. «Ничего не произошло» после залпа — сначала подозревай лок, а не логику:
  перепроверь теми же запросами по одному, прежде чем писать дефект.
- **Коды внешних интеграций бери из кода шлюза, а успех меряй эффектом.** Шлюз маппит внешние коды на
  внутренние имена и на неизвестный код обычно отвечает **200, ничего не сделав** (так ушли в никуда три
  варианта кода события, пока таблица не нашлась в ⟪ADAPT: где у вас маппинг внешних кодов — напр.
  контроллер вебхуков шлюза⟫). Внешний код ≠ внутреннее имя — не подбирай наугад.
- **Сценарий, зависящий от внешнего потока, заказывается точкой входа**, а не запросом: вход в одной фазе
  потока даёт один исход, в другой — другой. Приёмы — `references/stage-trading-harness.md`.

**Журнал мутаций:** каждую правку стенда (запись через API/ключ/событие/флаг) **записывай** — для отката (Ф9).

## Фаза 5 — Мониторинг логов  (опц., за профилем)

- **Логи и метрики — только тем доступом, что даёт профиль:** ⟪ADAPT: лог-агрегатор (Kibana/Loki/…) и метрики
  (Prometheus/Grafana) — чем ходить, где ключи⟫. Работай дисциплиной агрегатора: сначала поля/счётчики/дайджест,
  поиск — только с целью (id сущности/пользователя, сервис, окно, симптом); логи в контекст не льём. Доступа или
  ключа нет → честно **N/A** + `[нужны данные]`, «за N дней» тогда недостижимо.
- **Зачем это Ф8/Ф9:** строка лога сервиса с `user_id`/`account_id`/`deal_id` и временем — первичка для гейта
  атрибуции и для трейса в баг-репорте; служебные события (загрузка/обновление снимков, консюмер событий,
  фоновые воркеры) видны только там.
- Есть доступ → запускай мониторинг **фоном отдельным агентом**: раз в ~10 мин снимает свежие срезы
  (`--since=<окно>`) по затронутым сервисам, агрегирует ошибки/варнинги по паттерну (нормализуй числа),
  топ-N с счётчиками. НЕ полагайся на долгий `-f`/foreground-`sleep` — периодические срезы/until-условие.
- Различай **свой тест-трафик** (invalid_*/throttle из твоих негативов) от **реальных дефектов**.

## Эталон-мастер и порядок сбора  (общее для Ф6–Ф8)

Ф6 (состояние) и Ф7 (негативы) сравнивают ветку с **эталоном-мастером**. Эталон поднимается ОДИН раз для
обеих. Гейт атрибуции ниже — сквозной, применяется к любой находке (Ф6–Ф8).

**Когда differential применим.** Только для **изменённого существующего** поведения. Для **net-new**
(новый эндпоинт/событие без аналога на мастере) эталона нет: оракул = спека/код/заметки, **одиночный**
прогон. Не выдумывай «мастер-baseline», где его нет.

**⚠️ Две проверки предпосылок ДО любого сравнения — каждая сама по себе даёт ложный зелёный:**
1. **Формат запроса задаёт КЛИЕНТ, не новый сервис.** Когда роут переезжает за прокси/канарейку или логика
   переносится между сервисами, конверт тела, имена полей и обязательные заголовки бери из **валидации СТАРОГО
   хендлера** (что реально шлют клиенты сегодня: allow-list легаси-модели, её DTO, документация API), а не из
   swagger/DTO нового сервиса. Пейлоад, скопированный с нового сервиса, проходит его валидацию и создаёт иллюзию
   рабочего пути, а запрос реального клиента отбивается. Дешёвый различитель: пошли тело **в форме клиента** на
   обе стороны — эталон должен дойти до доменной логики (ошибка по состоянию: «expired»/«not found»), а не
   отбить по форме. Отказ по форме на ветке там, где эталон доходит до домена, = слом контракта, не «негатив».
2. **Эталон может ничего не делать — установи, что он что-то делает, до заявления паритета.** Прежде чем писать
   «старое поведение не изменилось», сними **сайд-эффекты эталона** (запись/событие/исходящий вызов/строка лога).
   Их нет — эталон пустой no-op: «ничего не изменилось» тривиально верно, сравнивать нечего. Пустой эталон
   переворачивает смысл задачи: миграция не *переносит* поведение, а **включает** его (мёртвый код, флаг,
   годами выключенный, метод, закомментированный до внешнего согласования) — это отдельный риск релиза, назови
   его в отчёте явно, не пряч за PASS. Проверяй, что эталон реально доходит до своего даунстрима, а не просто
   отвечает успехом.

**Режимы:**
- **A — параллельный эталон** (предпочтительно): ветка на слоте-ветки, мастер на прод/main-слоте →
  снимаешь оба одновременно, переключений нет.
- **B — последовательный** (нет параллельного эталона): собери ВСЮ мастер-сторону за один проход
  (срез состояния + baseline негативов) → одно переключение слота на ветку (деплой делает CI/пользователь,
  **не** ты) → пере-сверь образ=ветка (Ф2) → один ветка-проход.
- **C — эталон недостижим / нет доступа к сырому стору** (частый дефолт для БД/кэша/шины): differential по
  сырому стору невозможен. Оракул = **спека/код/заметки**; прогоняй одиночно на ветке, сравнение с мастером
  по стору **честно помечай непроверенным** (⛔). Наблюдаемое через API/WS состояние сравнивай (это доступно).
- **D — differential без слотов, экспериментом на ветке** (нет ни параллельного эталона, ни права
  деплоить мастер — частый случай для «перенос сервиса»/рефактор): **сэмулируй мастер-поведение на самой
  ветке и сравни эффект.** Две техники: (1) мастер готовит состояние заранее (eager), а ветка — лениво →
  **воспроизведи подготовку вручную** (прогрей строку/кэш/счёт) и померь, меняется ли эффект: не меняется
  → изменение MR ни при чём; (2) **изолируй изменённый путь от неизменного** (гони тот же негатив на чистой
  изменённой ручке и на смежной нетронутой) — эффект живёт на нетронутой → не регрессия. Это контролируемый
  эксперимент, а не прогон мастера, но снимает/подтверждает атрибуцию доказательно.

### ⚠️ Гейт атрибуции — каждая находка проходит его ПЕРЕД тем, как стать «дефектом MR»

Задача QA ветки — не «набрать проблем», а доказать, **какие из них создал именно этот diff**. Мастер
сейчас не чинят: pre-existing-баг, поданный как регрессия MR, — ложная тревога (разработчик по праву
назовёт такой разбор бесполезным). На каждый плохой сигнал (5xx, расхождение, странность) — три вопроса:

1. **Есть ли причина в диффе?** Начни с самого дешёвого: `git diff --stat <base>..<branch> -- <путь>` —
   пять секунд, а снимает половину подозрений; пустой вывод = поведение не из этого MR. Не пусто —
   покажи изменённую строку/схему на ЭТОМ пути. Появилась ли функция в ветке, отвечает
   `git grep -c "func X" origin/<main-branch>`.
2. **Воспроизводится вне изменённого кода / при сэмуляции мастера?** (режим A/B — прогоном мастера; режим
   D — сэмуляцией на ветке). Воспроизводится → pre-existing.
3. **Правдоподобная причинная история ≠ доказательство.** Выдвинул гипотезу «diff сломал X» — **поставь
   эксперимент, который её ОПРОВЕРГНЕТ** (прогрей то, что мастер готовит заранее; изолируй изменённый путь).
   Устояла под опровержением — только тогда регрессия.

⚠️ **Грабля сравнения с мастером:** `git fetch origin` умеет упасть на несуществующем удалённом рефе
(настроенный refspec репы) и при этом **не обновить** локальную копию основной ветки — вывод «в мастере
этого нет» окажется ложным. Тяни явным рефспеком:
`git fetch origin "+refs/heads/<main-branch>:refs/remotes/origin/<main-branch>"`.

Вердикт каждого дефекта в отчёте несёт **одну строку атрибуции**: `в диффе? · репро мастера · вывод`.
Не доказал, что diff создал, — severity вниз, метка pre-existing/наблюдение, **на MR не вешаем**. Это
относится и к находкам Ф8 (5xx/аномалия в позитивах), не только к differential-негативам Ф7.

## Фаза 6 — Сверка состояния «мастер ↔ ветка»  ⚠️ если затронуты хранилища/события

Если импакт (Ф1) показал изменения в данных/событиях — сравни состояние на мастере и на ветке под теми же
сценариями пополевно. Изменения в сторе не видно по коду ответа — молчаливая регрессия опаснее всего.
**Не затронуто — N/A с причиной.**

- **По умолчанию — наблюдаемое состояние через API/WS** (баланс, сущности, состояние через те же
  сокеты/ручки, что и клиент): срез на main-слоте и на слоте-ветки под тем же сценарием → пополевый diff
  (значения, наличие/число событий, пустые/лишние поля). Запиши снимки в файлы (`storage-baseline.md`/
  `storage-branch.md`), сравнивай точно, не по памяти.
- **Перечисляй, что появилось на самом деле, а не что ожидал:** список реальных ключей/строк/событий/полей
  (листинг, не зондирование заранее предсказанных). После пополевого диффа сравни **множества** созданного
  эталон↔ветка: лишний или недостающий элемент невидим, если проверять только то, что заранее внёс в список.
  Наблюдаемое поведение может совпадать при разном составе — «лимит срабатывает» верно на обеих сторонах, а одна
  завела лишний счётчик или общий ключ там, где другая — per-subject.
- **Сырой стор (БД/кэш/шина)** — только если профиль даёт доступ; иначе режим C (см. выше).
- **Строгий случай — миграция/перенос 1:1:** ожидание — полное совпадение значений; любое расхождение —
  баг миграции.
- **⚠️ Существующие данные ДО изменения** (для миграций/precision/формата/схемы): проверь mixed-state —
  `старые данные + новый код`, `новые + новый`, `старая сущность изменена новым кодом`. Ловит «новое ок, а
  старое поехало» (напр. precision у существующих сущностей). Отдельные Check ID (`Existing-data`), не в общей регрессии.

## Фаза 7 — Дифференциальный прогон негативов (эталон → ветка)  ⚠️ ключевая проверка error-поведения

Цель: ветка **не сломала/не ухудшила** обработку ошибок, и каждая ошибка **логична и понятна юзеру**.
Гоняем ВСЕ негативы тест-дизайна (Ф3) по **изменённому** поведению дважды и сравниваем. net-new — оракул
спека/код, одиночный прогон.

1. **Baseline на эталоне** (прод/main-слот): каждый негатив → снимок (HTTP/gRPC-статус, машинный код/тип
   ошибки, тело/структура, человекочитаемое сообщение + локаль, тайминг, сайд-эффекты). В файл
   `negatives-baseline.md` с ключом кейса.
2. **Ветка** (слот-ветки; пере-сверь образ=ветка). Тот же субъект/фикстуры/порядок/входы; для одноразовых
   артефактов — эквивалентные свежие на обоих прогонах.
3. **Повтор тех же негативов** → `negatives-branch.md`.
4. **Diff эталон↔ветка** пополевно. Классифицируй: **совпало** (нет регрессии — тоже результат);
   **by-design** (заявлено — сошлись на источник); **регрессия** → баг (Ф9). Красный флаг: понятная ошибка
   на эталоне → 5xx/пустой/таймаут/новый неописанный код на ветке.
5. **Понятность ошибок (UX) — на обоих прогонах, даже без расхождений:** 4xx не 5xx; осмысленный машинный
   код + человекочитаемое локализованное сообщение; без утечки внутренностей (стек/SQL/имя таблицы); без
   «немого» 5xx/timeout. Было на эталоне — **pre-existing** (severity ниже, но фиксируй); новое на ветке —
   регрессия.

## Фаза 8 — Прогон остальных проверок (позитивы + сайд-эффекты)

- **Перед первым мутирующим шагом — декларация мутаций** (см. «Режим запуска и безопасность»): напечатай,
  что запишешь на стенд (Check ID с `Mutating=да`).
- Иди по матрице: **запрос → факт → ожидание (оракул) → PASS/FAIL → заметки**. Обновляй матрицу.
- **Сверяй состояние, не только код ответа:** после success — запись/событие/сессия/ключи (значение+TTL),
  метрика. Затронуты хранилища — сверка мастер↔ветка и для позитива (Ф6).
- **Rate-limit-aware:** не долби подряд — разноси или бери свежий субъект на rate-limited группу.
- **Time-gated** (эскалация задержек) — через устойчивый механизм, не foreground-sleep; часы/сутки —
  подтверждай по коду + честно «live не прогонялось».
- **Чтения — ограниченные и не деструктивные** (`SELECT … LIMIT`, `SCAN` не `KEYS *`, шина по count/offset).
- **Факт ≠ гипотеза:** рестарты пода = *потенциальная* нестабильность, не «упал», пока не подтвердил.
  Аномалия ≠ баг, пока не исключил дрейф/чужой трафик/фикстуру. В отчёте — раздельно.
- **Root-cause при 5xx/расхождении/аномалии — два гейта, иначе это гипотеза, а не причина.** (1) **Репро:**
  сделай симптом воспроизводимым по требованию — минимизируй вход (убирай заголовки/поля/шаги по одному);
  «флак» — не случайность, а непойманный триггер: меняй по одной оси (порядок/тайминг, параллельно/
  последовательно, свежий/переиспользованный субъект, конкретные данные). Не воспроизвёл — так и пиши, причину
  не выдумывай. (2) **Переключение:** причина доказана, когда её включение даёт симптом, а выключение убирает —
  повторяемо. Между гейтами — **бисекция, не перебор**: слой (клиент → гейтвей → сервис → даунстрим → стор: где
  значение впервые неверно; логи через агрегатор из профиля, Ф5), время (`git bisect` по `master…ветка`, дифф
  образа/конфига с последним рабочим), вход (какое поле переключает), конфиг/флаг, данные/состояние (шард,
  строка, TTL, остаток фикстуры). **Одна гипотеза за раз:** сформулируй, предскажи, что увидишь если верна и
  если нет, поставь самый дешёвый различающий зонд, меняй одно. **Причина ≠ строка, что бросила:** иди вверх по
  цепочке до самого раннего расхождения; стоп — когда следующее «почему» уходит из-под тестируемого изменения.
  **Классифицируй:** дефект ветки · by-design · дрейф стенда/инфра-гейт · фикстура/тест-данные · другой
  слой/даунстрим · баг харнесса — причина вне ветки тоже валидный результат, назови владельца. Затем **blast
  radius** (что ещё ломает та же причина) и **проверка-после-фикса** (какой Check ID должен позеленеть). Дефект vs
  by-design при сомнении — спроси разработчика.
- **Одну сущность сверяй на всех поверхностях, где она видна.** Если объект рисуется в нескольких местах
  (разные экраны/вкладки UI, сообщение бота или уведомление, ответ API, первичная запись) — выпиши его
  ключевые поля везде **рядом** и сравни. Так родились три находки из четырёх на живой задаче: две разные
  цены закрытия у одной операции, полный объём в одном месте против остатка в другом, процент от разных
  баз. Расхождение между поверхностями — дефект даже тогда, когда каждое число по отдельности «верное».
- **Прогони находку через гейт атрибуции** (раздел «Эталон-мастер»): создал ли её ИМЕННО diff. 5xx с
  правдоподобной причиной — ещё не регрессия MR; нужен опровергающий эксперимент (режим D). Не доказал —
  pre-existing/наблюдение, не дефект ветки.

## Definition of done — когда задача «протестирована»

Не «прогнал сколько успел», а явный гейт. Готово только когда верно ВСЁ (иначе — не готово, и отчёт говорит это
прямо):
1. У каждого **critical/high REQ** (Ф1.5) — **PASS** либо задокументированный **⛔BLOCKED** с причиной; medium/low —
   покрыты или явно отложены в отчёте. ≈PASS-EQ засчитывается только с записанным доказательством эквивалентности.
2. Все **не-PASS** классифицированы: FAIL / PARTIAL / BLOCKED / NOT-RUN / by-design — молчаливых пропусков нет.
3. Гейт **Ф3.5** прошёл по финальной матрице, открытых HIGH нет (или пользователь их явно принял).
4. **Журнал мутаций откачен** (Ф9): стенд восстановлен, базовые сценарии снова работают.
5. Отчёт содержит **закрытие трассировки** (Ф9 п.1а): дыры покрытия и расхождения REQ↔код названы явно.
6. Найденные дефекты — с severity, шагами и строкой атрибуции; после фикса перепроверены, где возможно.

## Фаза 9 — Отчёт, баг-репорты, откат

1. **Отчёт** в папку задачи рабочего воркспейса: **`tasks/qa-backend-<тикет>-<слаг>/report.md`** (раскладка
   delivery-флоу — `../delivery_orchestrator/references/workspace-layout.md`). Итоговая таблица
   `# | REQ-ID | Проверка | Приоритет | Метод/ручка | Ожидание | Факт | Статус | Заметки` + резюме (PASS/FAIL,
   баги по приоритетам файл:строка, что на ручную, что ⛔BLOCKED и почему, сигналы логов, принятые допущения
   headless-режима). Критичное — в начало. Зафиксируй стенд и выкаченные версии сервисов, против которых гонялось
   (вывод `verify-stage-deploy.sh`).
1а. **Закрытие трассировки (Ф1.5) — обязательный блок отчёта:**
   - **Требования без покрытия** — REQ без PASS-кейса (нет теста вовсе или все ⏳/⛔). Это дыры покрытия, не «ок
     по умолчанию».
   - **Требования, разошедшиеся с кодом** — REQ со статусом «расходится»/«неоднозначно» из Ф1.5 (находки до
     прогона): что заявлено, что в коде, кого спросить.
   - **Покрытые по аналогии** — каждый ≈PASS-EQ отдельно: что подменили и почему это тот же класс
     эквивалентности. То же для непрямых PASS (вывод через соседнюю проверку).
   - Сводка: `покрыто / по аналогии / частично / не покрыто / непроверяемо` из N требований. Не сливай в один
     «процент прошедших».
2. **Баг-репорт на каждый дефект** — шаблон `../qa_mr/references/bug-report.md` (severity, где, ожидание,
   факт+тайминги/логи, шаги воспроизведения, вероятная причина, что by-design/чужой слой). **Обязательна
   строка атрибуции** (`в диффе? · репро мастера · вывод` — см. гейт в «Эталон-мастер»): без доказанного
   «создал diff» дефект идёт как pre-existing/наблюдение, не как регрессия MR. Трейс для логов — `user_id ·
   entity_id · время · trace_id` (полными именами). После фикса — **перепрогони кейс**, пометь «перепроверено».
   - **Перепроверка фикса — отдельная таблица:** `кейс | живые числа | что дало бы старое поведение |
     сверка с первичным источником | статус`. Колонка «старое поведение» обязательна: она доказывает, что
     кейс вообще **различает** до и после. ⚠️ Сперва подбери вход, где старая и новая формулы расходятся
     заметно, — иначе PASS ничего не стоит. Пример: первый кейс дал 4.8684 против 4.869 (совпадение в
     пределах округления, доказательство нулевое), и пришлось строить различающий: 5.4928 против 5.4523.
   - Находку, которую починили, **не удаляй** — помечай ✅ с ссылкой на MR фикса и датой, исходный текст
     оставляй ниже. Отчёт читают и после мержа.
3. **Пиши плотно — отчёт читают люди, слоп читать неприятно.** Строже к себе, чем к коду:
   - Строка проверки = **действие + наблюдаемый результат + трейс**, не нарратив: «400 `invalid_request`,
     trace_id X» — не «корректно отклонил запрос с понятным сообщением».
   - **Витрина ≠ детали.** Итоговая таблица — одна короткая строка на ячейку; причины/доказательства — в
     тексте под ней и в `for-backend.md`. Слои не дублируют друг друга.
   - Вырезай AI-воду: преамбулы, хеджирование («вероятно, стоит отметить»), самопохвалу («тщательно
     проверил»), эмодзи-инфляцию, повторы. Оставляешь — только если несёт факт.
   - Числа и трейсы вместо прилагательных. Обычные слова, без калек (причина, не «рут-кос»; фоновая
     очередь, не «outbox»). Тех-параметры — полными именами (`entity_id`, не «id»).
4. **Evidence без секретов** — только плейсхолдеры.
5. **NOT-RUN не молчать** — каждый незапущенный Check ID явно `⏳NOT-RUN`, не FAIL и не пропуск.
   «done/verified/PASS» — только с наблюдаемым доказательством (Ф3). **Чужое свидетельство — не твой PASS:**
   «подтверждено тестом разработчика / дев говорит, что работает / покрыто его юнит-тестом» — это
   `code-verified` или **NOT-RUN** со ссылкой, никогда не PASS в твоей матрице. PASS значит, что критерий из Ф3
   наблюдал *ты*.
6. **Откат (teardown):** по журналу мутаций верни стенд в исходное (DELETE/восстановить/revoke).
   Throwaway-субъекты на dev можно оставить. Проверь, что базовые сценарии снова работают.
7. Обнови `hints.md` рецептами/граблями (и `backend-profile.md`, если изменилась карта). Черновое этой сессии (🌱)
   пиши в локальный overlay `hints.local.md` (вне плагина — переживает обновление); подтверждённое на второй
   задаче переноси в `hints.md` репы через MR плагина. Формат записи — короткий заголовок → точная
   команда/рецепт → в чём грабля; устаревшее переписывай, не копи дубли.
8. **Постоянная регрессия — другой артефакт, матрицу в неё не копируй.** Матрица одноразовая (в ней сверки
   стенда, грепы, разовые снимки паритета). Фича заслуживает долгой защиты — предложи durable-автотест через
   `/autotest` (durable e2e-автотесты; для чисто API-сценариев — харнесс `evidence/*` как основа): кейс
   выводится из бизнес-правила, а этот прогон — лишь свидетельство реальных значений. Строки матрицы,
   скопированные в сьюту, гниют на следующем рефакторинге.

## Красные флаги  ⚠️ поймал себя на одном из них — остановись и вернись на фазу

Провалы, ради которых существует этот плейбук; каждый привязан к фазе, которая его ловит.

- **Ложный PASS/FAIL на старом коде** — стенд отвечает старой сборкой; сверяй скриптом (Ф2) и пере-сверяй по фазам.
- **Паритет по памяти** — «помню, мастер отвечал X» вместо файла-снимка; дифф должен быть точным (Ф6/Ф7 →
  `*-baseline.md`).
- **Одиночный прогон выдан за паритет** — эталон не поднят, а отчёт намекает на сравнение; это режим C → ⛔.
- **Зелёный HTTP, непроверенный стор** — 200/OK без проверки записи/события/баланса = не PASS (Ф8).
- **Требование на веру** — спека/чат приняты за истину без сверки с кодом (Ф1.5).
- **Строка перечисления потеряна в пересказе** — таблица из N сценариев пересказана, а не перенесена; строка, что
  не влезла в формулировку, исчезла (Ф1.5 п.1а — пересчитай).
- **Один представитель выдан за покрытие** — один актив/валюта/страна прогнаны, группа объявлена покрытой без
  доказанной эквивалентности (Ф3 п.3а → ⚠️PARTIAL, не PASS).
- **Тавтологичное ожидание** — ожидаемый результат прочитан из фиче-ветки (или её юнит-теста), проверка умеет
  только согласиться с реализацией (Ф3 оракул → `OPEN`, спросить).
- **Свой план проверен своим автором** — матрица ушла в прогон без гейта Ф3.5; или после смены скоупа удалили
  только строки, на которые указали, вместо повторного прохода по всем REQ.
- **Молчаливые дыры** — незапущенный кейс показан как отсутствующий вместо NOT-RUN; непокрытое REQ прочитано как
  «ок по умолчанию» (Ф9 закрытие).
- **Аномалия = баг** — рестарты/5xx названы дефектом до исключения дрейфа стенда, чужого трафика, фикстуры,
  by-design и до гейта атрибуции (Ф8).
- **Троттл/санкция портит субъекта** — один субъект на несколько rate-limited групп; бери свежего (Ф8).
- **Инфра-гейт принят за логику приложения** — гео/IP-гейт «проходит» только потому, что внутренний IP в
  whitelist (профиль, infra-гейты).
- **«Запрос дошёл» прочитано как «обработан верно»** — новый сервис получил запрос, путь объявлен рабочим; на
  деле отбил пейлоад на валидации. И сравнение с эталоном, который ничего не делает. Оба — ложный зелёный:
  проверки предпосылок в «Эталон-мастер» до любого заявления паритета.
- **Усечённый инвентарь принят за полный** — `head`/`tail`/`LIMIT` на схеме (`DESC`), списке ключей, таблице
  роутов или дампе конфига прочитан как исчерпывающий и породил ложные гипотезы («такой колонки нет»). Инвентарь
  и схему не усекай; пришлось — скажи об этом и перечитай целиком до вывода.
- **Дыра фикстур выдана за находку** — «это состояние недостижимо штатным путём» — задача Ф4 (сидируй через
  API/вебхук/харнесс), не дефект продукта. Сначала попробуй сидировать; только если состояние недостижимо *даже
  сидированием* — это вопрос разработчику о мёртвом коде.
- **Свой тест-трафик прочитан как дефекты** — `invalid_*`/санкция/троттл от собственных негативов посчитаны
  ошибками сервиса (Ф5).
- **Секреты в evidence** — реальные токены/JWT/PII в отчёте/логах/чате; только плейсхолдеры (Ф9).

## Принципы

- **Read-only by default; деструктив — никогда.** Реальная гарантия — доступы (read-only ключ на репо,
  API-мутации только фикстурами, нет инфра-записи, прод не мутируем). Перед мутациями — декларация.
- **Источник истины по контрактам — код сервиса.** Ручки/заголовки/таблицы/формулы — из репо, не по памяти.
  **Ожидание** — из спеки/автора/продукта, не из фиче-кода (Ф3).
- **Требования не на веру.** Спека/чат — не аксиомы: разложи на REQ, сверь с кодом (Ф1.5), расхождение — находка
  до прогона. Каждое REQ → ≥1 кейс, каждый кейс → REQ; закрытие — в отчёте (Ф9).
- **Свой план проверяет чужой контекст** (Ф3.5), а покрытие считается по измерениям с доказанной
  эквивалентностью, не по одному представителю (Ф3 п.3а).
- **Не выдумывай; факт ≠ гипотеза.** Нет ручки/сервиса/ветки/репо — пиши прямо. Наблюдение ≠ вывод.
- **Атрибуция обязательна: доказывай, что дефект создал ИМЕННО этот diff** (есть в диффе + репро/сэмуляция
  мастера). Правдоподобная причина без опровергающего эксперимента — не вывод. Не доказал — pre-existing,
  не регрессия MR. Мастер сейчас не чинят: ложная регрессия дороже пропуска.
- **Отчёт плотный, без слопа:** действие + результат + трейс, витрина в одну строку, никакой AI-воды.
- **Секреты — не в файлах и не в evidence** (`.env`; в отчёт — плейсхолдеры).
- **Сверка состояния мастер↔ветка обязательна, если импакт показал изменения** (Ф6); не затронуто — N/A.
- **Дифференциал — для изменённого существующего**; net-new — одиночный прогон с оракулом код/спека.
- **Не ломай общий стенд** — журнал мутаций + откат, свежие субъекты.
- **Отчитывайся пошагово; веди живую матрицу** — «что не проверено» под рукой.
- **Пополняй `hints.md`** — скилл умнеет от сессии к сессии.
- **Язык ответа = язык пользователя** (по умолчанию русский); английский — только в том, что уходит в репо.
