# Харнесс сценариев, зависящих от внешнего потока

Про задачи, где исход определяется не твоим запросом, а **внешним потоком данных**: рыночные котировки,
курсы, показания устройств, телеметрия. Такие кейсы (сработал уровень / порог / таймаут по цене) нельзя
«просто попросить» через API — их надо **заказать**, войдя в нужной точке потока.

Скрипты под ваш API писать придётся самому: ручки, фикстуры и формат событий у всех свои. Ниже — приёмы и
грабли, которые от продукта не зависят. Готовый набор из четырёх скриптов (котировки + фикстуры + тайминг
записи + выстрел в момент события) занимает ~600 строк; писать его один раз и держать рядом с папкой задачи.

**Состояние с токенами тест-субъектов** держи в файле в папке задачи (не внутри плагина) и **в git не
коммить** — папки задач иногда версионируют.

## Ловим поток

- ⟪ADAPT: чем у вас читается внешний поток — WebSocket-канал котировок, SSE, брокер, polling-ручка⟫.
  Выясни это **до** тест-дизайна: от частоты и шага потока зависит, какие кейсы вообще достижимы.
- **Грабля авторизации канала:** гейтвей может рвать хендшейк из-за отсутствия «браузерного» заголовка
  (у нас — `Origin`, close 1008 без внятного текста), при этом сам поток отдавать **без авторизации**.
  Не трактуй обрыв как «нет доступа», пока не попробовал с заголовками как у веб-клиента.
- **Кэшированные REST-ручки для этого не годятся.** Сводки/чарты отдают агрегат с лагом и расходятся с
  живым потоком на проценты, а свечи имеют минимальный интервал. Реальное значение видно только в потоке —
  либо в поле только что созданной сущности (`price_open` открытой позиции и аналоги).
- Коды/формы событий канала берите из кода клиента (фронта), а не из документации: ⟪ADAPT: где у вас
  описаны коды сокет-событий и их payload⟫.

## Точка входа выбирает сценарий

Главный приём: **сначала замерь поток** (несколько минут наблюдения: min/max/шаг/размах), и только потом
решай, куда входить. Одна и та же логика из разных точек даёт разные исходы. На примере торговой стратегии
с уровнями «тейк выше входа / усреднение ниже / стоп ещё ниже»:

| Куда входим | Что получаем |
|---|---|
| у **дна** цикла | срабатывание верхних уровней, полный цикл «по своим уровням» |
| у **вершины** цикла | движение вниз → усреднение, стоп, перевод стопа в безубыток |
| в середине хода вверх | мгновенное срабатывание первого уровня — кейс «смазан», перезаходи |

Инструмент, который это даёт: **ожидание абсолютного значения в потоке и выстрел по достижении**
(«ждать, пока значение станет ≤ / ≥ X, затем послать событие»). Вариант «поймать локальный экстремум и
разворот» звучит умнее, но на грубом шаге потока (3 % за тик) почти никогда не срабатывает — окно в три
последовательных тика не набирается. Абсолютный уровень надёжнее.

Второй инструмент: **выстрел в момент события** — опрос состояния сущности до признака (сработал первый
уровень), и сразу отправка следующего события. Окно живёт секунды, руками в него не попасть.

Третий: **замер тайминга** — сколько прошло между фактом во внешней системе и его отражением в записи
сервиса. Пригодится, чтобы не принять нормальную задержку за дефект синхронизации: у нас «пятиминутный лаг»
оказался чужими параллельными событиями, а в чистом прогоне запись реагировала за 1–2 секунды.

## Грабли прогона

- **Залп событий на один субъект теряется.** Обработчик берёт лок (`SET NX EX` без ожидания и повторов):
  пока первое событие держит лок, остальные молча выходят — без лога и без сообщения пользователю.
  Разноси выстрелы по времени; «ничего не произошло» на залпе — сначала подозревай лок, а не логику.
- **`200` от вебхука не значит «принято».** Шлюз отвечает 200 и на неизвестный код события. Успех проверяй
  по наблюдаемому эффекту, а коды бери из кода шлюза: ⟪ADAPT: где у вас маппинг внешних кодов на внутренние
  имена⟫. Внешний код ≠ внутреннее имя, по имени сторона/смысл не угадывается.
- **Ручки истории часто требуют явный фильтр** (у нас — `account_id`), иначе отвечают пустым списком,
  который читается как «событий не было».
- **Ограничения стенда — измеряй числом.** Фикстуры живут ограниченное время (у нас сессии автостопаются
  примерно через час), амплитуду и шаг синтетических данных задаёт администратор стенда. Не лезет сценарий
  в это окно — не хорони кейс, назови ограничение числом и попроси поправить стенд (`SKILL.md`, Фаза 3
  пункт 7).
- **Токены тест-субъектов живут ограниченно**, и UI-логин может инвалидировать токен, которым ты ходишь по
  API. Для UI-прогона держи отдельного субъекта.
